# NPC RTL 编码规范

最后更新：2026-09-26

本文档是 NPC RTL、可综合系统模块及仿真行为模型必须遵守的命名与代码组织检查表。
设计位于 `npc/vsrc/riscv`。全部模块及本轮检查结果见
[设计模块总览](../architecture/RTL_MODULE_MAP.md)。

## 目录、文件和模块名

- 设计模块和 package 使用 `riscv_` 前缀，不用 `riscv32_` 或 `riscv64_` 表示项目身份。
- 文件名与其中的主要模块或 package 同名，单词使用小写并以下划线分隔。
- `core` 保存处理器核，`system` 保存平台连接，`sim` 保存仿真模型，`experiments` 保存
  独立实验。实验不会因为放在设计目录中就自动加入正式构建。
- `core/` 下只保留整核连接；子目录按 `frontend`、`decode`、`issue`、`execute`、`memory`、
  `writeback`、`control` 分类。历史流水级放在 `experiments/pipeline`，保留来源。
- 模块名优先使用已约定的短名：控制器用 `_ctrl`，选择器用 `_mux`，流水寄存器用 `_reg`；
  例如 `riscv_hazard_ctrl`、`riscv_operand_mux`、`riscv_id_ex_reg`。不重复堆叠同义职责。
- 构建选择使用 `PROJECT=riscv`，当前硬件配置仍为 `rv64-edge-ai`，其名字不代表 AI 能力。
- `top`、DPI 函数和外部平台要求的端口名按既有接口保留；独立实验可在功能名中表达真实
  数据宽度，例如 `riscv_alu32_for_sta`。

## 核心原则

名称必须描述信号当前承载的硬件含义。在模块边界处，读者无需查找赋值语句，就应能
判断信号来自哪里、去往哪里，或者它表示什么事件或数据。

## 命名规则

1. 按对象当前承载的硬件信息或执行的架构操作命名。不能只根据实现机制、较早的产生者
   或编码细节命名。
2. 只添加消除歧义所需的限定词。根据上下文，可以包含来源、目的地、协议角色、操作、
   架构所有者、时钟域、物理单元或数据形状。
3. 状态名称说明实际记录的事实。记录握手是否发生时使用事件名称；只有确实表示整个操作
   完成时才使用 `done`，表示成功或失败时同样必须有明确条件。
4. 架构和协议术语具有精确定义时，使用标准术语，不能用局部同义词替代。
5. 保存状态的寄存器按其保留的信息命名，事件历史按其记录的事件命名。固定配置常量与
   运行时变化状态必须明确区分。
6. 当集合形状会影响理解时，按对象逐位表示的打包位集合使用 `_vector`，非打包数组使用
   `_array`，单个元素的编码编号使用 `_index`。普通地址和数值虽然也是多位信号，不需要
   因此加 `_vector`。名称要能区分整个集合与选中的一个元素。
7. `valid` 表示协议或数据有效；`present` 表示某项内容或状态当前存在。单拍事件用
   `*_event`，`valid && ready` 的接收条件用 `*_handshake`，已保存的事件历史用
   `*_occurred_q`。不要把协议有效位改成状态位，也不要把组合事件命名成寄存历史。
8. `_i`和`_o`只用于模块端口；`_q`和`_d`只用于寄存器当前值及其组合下一值；`_t`用于
   类型，`_e`用于枚举类型。
9. 避免含义宽泛的词，除非限定词已经使它在当前模块中只有一种解释。读者不能依赖赋值
   语句才能区分一个名称的两种合理含义。
10. 重命名时必须同步修改所有相关引用：声明、端口、赋值、注释、TODO、断言、波形
    标签和调试输出。
11. 参数名称说明对象与单位，沿用当前配置的约定：数量用 `_COUNT`，位宽用 `_WIDTH`，
    字节容量用 `_BYTES`，例如 `ROB_ENTRY_COUNT`、`PADDR_WIDTH`、`ICACHE_LINE_BYTES`。
    局部变量采用对应小写形式，不使用缺少对象说明的 `SIZE` 或 `NUM`。
12. 彼此独立的架构宽度必须使用独立名称，例如 `XLEN`、`INSTR_WIDTH`、`PADDR_WIDTH`
    和 `MEM_AXI_DATA_WIDTH`，不能因当前数值相同而合并。新增虚拟地址等宽度时再定义相应名称。
13. 选择目标时用 `select`，解释指令编码时用 `decode`；不要仅为统一词形而改变准确的含义。

## 命名审查

以下例子对应当前代码，名称只在实际含义匹配时采用：

| 对象 | 命名示例 | 阅读时能确定什么 |
| --- | --- | --- |
| 架构寄存器数组 | `gpr_array_q` | 保存多个寄存器当前值，索引选其中一个 |
| 每组缓存的替换路索引 | `replacement_way_index_array_q` | 数组每项保存一个路编号 |
| 多目标选择位 | `read_target_select_vector` | 每一位表示对应目标是否被选中 |
| 选中的目标编号 | `read_target_select_index` | 一个编码后的目标编号，不是位集合 |
| 已发生的写数据事件 | `write_last_data_occurred_q` | 本事务的最后一个数据 beat 已握手，不等于写响应完成 |
| 完整维护操作完成 | `clean_done_o` | 维护流程结束；成功与否还需检查对应错误信号 |

标准协议字段、指令字段和有明确含义的谓词函数可以保留惯用名称，例如 `ar.len`、`opcode`
和 `is_link_register()`。不要仅凭字符串匹配机械改名；特别要区分状态、事件和条件判断。

接受一个新名称前，检查：

- 当来源或目的地会影响理解时，名称能否明确指出它？
- 名称是否精确描述所表示的请求、响应、状态或事件？
- 在当前模块中，同一名称是否可能被合理地解释成两种含义？
- 在使用位置，集合是否能与标量或编码索引明确区分？
- 当数值依赖时钟域或物理单元时，名称是否明确指出了它们？

如果第三个问题的答案是“是”，必须进一步限定名称。

## 代码组织规则

1. 三段式状态机固定按以下源码顺序编写：
   - 第一段：根据寄存器当前状态产生组合输出。
   - 第二段：组合状态转移及寄存器下一值逻辑。
   - 第三段：时序状态及寄存器更新逻辑。
2. 每个组合逻辑块必须先给出完整默认值，再进行依赖状态的覆盖。状态转移块默认令每个
   `_d`等于对应的`_q`；输出块默认将输出设为无效值或其他明确定义的值。
3. 辅助函数、派生条件、事件表达式或地址计算应紧邻使用它的功能块之前。若相邻的多个
   功能块共享它，则放在这些功能块正前方、名称明确的共享区中。
4. 同一功能单元的声明、派生信号、组合逻辑和时序更新应彼此靠近。不能仅因为数据类型
   相同，就把互不相关的辅助信号或全部模块寄存器集中到远离其使用位置的全局区域。
5. 当拆分能提高局部可读性时，按功能和负责更新的状态组拆分时序逻辑。由同一下一值逻辑
   控制的寄存器，应在附近的时序块中更新。不能用一个巨大的时钟块更新互不相关的状态组。
6. 一个信号只能由一个过程块驱动。中间组合值可以在不同块中计算，但打包输出或逻辑上
   原子的接口必须有一个明确的唯一所有者。
7. 注释和教学TODO必须紧邻所描述代码的准确插入位置。读者应能直接在TODO下方实现，
   无需寻找其他位置。
8. 相关声明、赋值、端口和`case`项保持列式对齐。空行用于分隔语义组，不能随意分组。
9. 实现新的架构模块前，先在
   [`npc/docs/microarchitecture`](../microarchitecture/README.md)下创建或更新其
   设计记录。接口规则和已选方案写入设计记录；可复现的命令和测量结果追加到实验日志；
   有证据支持的可复用经验追加到学习日志。源码注释只解释局部RTL行为，不能成为模块级
   架构决策的唯一记录。
10. 参数只从统一配置入口进入模块。模块内部使用 `localparam` 计算派生宽度，并在构建展开
    时检查实际需要的整除关系、最小容量和索引范围；只对确有要求的参数检查 2 的幂。
11. 可扩展的way、bank、lane和队列项使用数组及`generate`组织，不能复制带数字后缀的
    信号或实例。项目只承诺命名配置通过完整回归，不承诺任意参数组合均合法。
12. top只负责实例化、连接和配置选择。功能状态、协议转换、仲裁策略和错误处理必须归属
    明确模块，不能作为零散组合逻辑滞留在top。

## 一个功能块如何排布

阅读一个功能块时，应尽量在相邻代码中看到：

1. 一两句职责说明，以及该功能使用的类型、参数和状态声明。
2. 紧邻使用处的辅助函数、地址计算和握手条件。
3. 根据当前状态产生的输出。
4. 状态转移与寄存器下一值计算，先给默认保持值。
5. 对应的时序更新，以及检查该功能的断言或相邻验证说明。

这是按功能组织的顺序，不要求把全文件的输出、全部状态转移和全部寄存器更新各自集中成
三个巨大区域。两个独立状态机可以各自完整呈现三段；共享接口输出仍须由一个过程驱动。

纯组合 ALU、简单选择器、寄存器堆和 valid/ready 流水寄存级按自身结构编写，不需要人为
添加枚举状态机。`always_comb` 防止意外存储；确实需要锁存器时使用 `always_latch` 并明确
开关条件、数据保持和时序验证，不能靠缺少默认赋值隐式产生锁存器。

注释解释当前代码的条件、原因和限制。未来模块拆分写入设计记录，教学 TODO 则放在需要
填写的位置上方。过期阶段编号和已经完成的 TODO 要及时移除，不能让读者依照旧注释误改代码。

## 排版如何保持一致

当前工作区使用 `bmpenuelas.systemverilog-formatter-vscode`，通过
[`sv_format_wrapper.py`](../../../../.vscode/sv_format_wrapper.py) 调用 Verible，并补充连续赋值
与常量的列对齐。结构体成员、端口、case 项和相邻赋值按功能分组对齐，换行继续缩进。
赋值首行可以对齐，续行保留 Verible 按表达式结构给出的缩进，不因左值较长而整段向右平移。

条件和其控制的赋值分行书写，赋值缩进一级；非空 `case` 分支的赋值放在标签下一行。
状态机按输出、下一值和寄存器更新排列；组合读口与结果选择放在对应状态更新之前。
不为排版交换有顺序依赖的过程语句，也不把不同状态的更新合并成一个大时序块。

格式器只处理排版，不能判断命名含义、模块职责或注释是否过期。修改格式后仍要检查差异；
大范围整理应检查代码标记保持一致，并运行相关 lint 与回归。不要为了对齐跨越无关功能组，
也不要为了让每条赋值只有一行而取消必要换行。

## 寄存器、等待与旁路检查

每次新增、修改或评审 RTL，都对受影响的数据通路及其上下游接口执行本节检查。
不要求为小改动新增整篇文档；在现有模块说明或验证记录中写清实际取舍即可。

1. **每组状态、每个等待都要有电路理由。** 区分算法状态、在途事务身份、反压缓冲和
   时序边界。等待必须对应未就绪的数据、被占用的资源、协议/架构顺序或已验证的时序
   需要；模块边界、FSM 写法习惯和未实现的未来通用性不能单独成为理由。
2. **先检查条件已满足时能否推进。** 检查空缓冲直通、旧项出队与新项入队、请求接收
   与下游发出、最后必要响应与完成、前递，以及维护阶段交接。数据可用、资源允许时，
   不无理由地先存一拍再处理；反压时才需要保存的请求不应强制所有请求经过额外一级。
3. **旁路必须覆盖完整事务语义。** 同时处理载荷、有效性、身份和异常；检查同步阵列
   同址读写、字节合并、最后一拍与新请求同时到达、反压、flush、复位及错误。
   保证旧响应不被新请求替换、请求不重复、副作用只发生一次，并检查组合环与新增路径。
4. **删状态前核对消费者和时序。** 优先复用已有事实、缩窄未使用字段，消除重复计数
   和无功能接线。派生寄存器、缓冲和独立运算器若能改善时序、并行度或面积，可保留，
   但须说明用途。共享函数不等于共享硬件；相同表达式也不等于综合后存在重复电路。
5. **先确认等待影响负载，再决定复杂旁路。** 记录触发次数、当时是否已有下一请求、
   资源是否可接收及预计节省周期。按全部 miss 数乘一拍只能作乐观估算，不能当作实测
   收益；统计范围须一致，不能把整程序事件数直接套入 Total 或 Scored 窗口。
6. **按目标保留改动。** 纯源码整理以等价和可读性验收；功能旁路以正确性为前提，
   比较同条件周期数、面积、通过时序的频率及执行时间。面积优先与速度优先的取舍要写清；
   周期小幅减少但时间变长、面积增加或维护明显变难时，不自动保留。收益不足或尚未测量
   可以保留原结构，并说明理由；不为了旁路覆盖率增加硬件。
   若提前请求反而变慢，应先区分硬件仲裁与仿真延迟换算的影响。计数准确不等于模型物理
   准确；不能仅凭有偏的模型判定并发更差，也不能为提高分数新增等待。
7. **每次改结构都清理旧描述。** 删除失去用途的状态名、信号别名、旧注释和重复说明；
   按实际数据流把选择逻辑、运算/阵列接口和所属状态放在相邻位置，反馈路径明确分组。
   有语义或平台契约作用的接线边界可以保留；历史实验按目录归档，不按未被实例化删除。

## 删除冗余和增加旁路

- 删除状态前，列出它的写入条件、读取者和最后使用时刻。无人读取的字段应连同端口、
  断言和说明一起删除；不能删除用于不同流水周期的数据副本。
- 共用缓冲必须指定唯一所有者，并说明从哪次握手到哪次握手保持稳定。消费者需要更长
  生命周期时，先修改协议；不能只删除它的寄存器。测试必须覆盖消费者反压和错误恢复。
- 相同且无状态的计算可以放到共同 package。位宽相同但含义不同的状态或接口不能合并。
- 增加旁路时说明生产者何时产生有效值、消费者在哪拍使用、多个来源的优先级，以及新增
  组合路径。先用依赖指令或连续请求测量收益，再比较同配置面积和时序。
- 结构优化分别报告功能回归、程序周期和综合结果。RTL 位数减少、源码变短、文件减少
  都不能单独证明映射面积或能耗下降。

## 代码组织审查

接受一个模块前，检查：

- 每个状态机是否依次呈现输出逻辑、转移逻辑和时序更新逻辑？
- 派生条件是否位于赋予它具体含义的功能块附近？
- 是否能在局部范围内从`_q`经过`_d`追踪到对应寄存器更新块？
- 每个信号是否只有一个明确的过程所有者？
- 每个TODO是否都能在它所在的位置直接实现？
- 参数是否带有单位，并能追溯到唯一配置入口？
- 改变参数后，数组形状、循环边界、断言和测试是否同步变化？
- top中是否仍存在应由功能模块或adapter拥有的状态和策略？
