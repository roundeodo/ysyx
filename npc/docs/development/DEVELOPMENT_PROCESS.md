# NPC 开发流程

状态：当前开发指导

最后更新：2026-09-27

程序功能与性能运行统一经过完整 ysyxSoC，使用校准后的外部存储延迟；默认配置和入口见
[SoC 测试说明](../verification/SOC_TESTING.md)。单元 testbench 用于定位与协议验证，
不替代整机程序验证，不提供正式性能结论。正式性能使用 train，开发筛选可先使用 test。

## 1. 一次修改要说明什么

先写清要解决的问题、准备修改的模块，以及如何判断修改正确。工作量大的模块分步完成，
每一步都保留可运行、可检查的结果。项目阶段以 [架构与开发路线](../architecture/ARCHITECTURE_PLAN.md)
为准，不要求每个任务都先找到 AI 应用瓶颈。

| 任务类型 | 开始前需要说明 | 完成后需要提供 |
| --- | --- | --- |
| 新功能或学习实现 | 要掌握的机制、功能范围、接口和验证方法 | 对应测试、实际行为及仍有限制 |
| 错误修复 | 复现条件、错误现象和预期行为 | 修复前后的结果，必要的回归 |
| 性能优化 | 基准程序、当前数据、推测的瓶颈和改动变量 | 同条件比较，周期、面积或时序的收益与代价 |
| 命名、注释或文档整理 | 哪些内容难懂、过期或不一致 | 引用、名称、结构和事实的一致性检查 |

功能实现可以先有机制目标；性能收益只能在测量后下结论。普通文字修改无需运行整套 RTL
回归；接口、指令语义或时序逻辑修改则需要相应验证。

## 2. 开展一次开发

### 第一步：确认范围

阅读相关设计记录和当前源码，确认已有行为、缺失能力和本次任务。只把当前检查点所需的
参数、接口和错误处理确定下来；未来功能保留为待研究事项。

### 第二步：查清关键机制

涉及 ISA 和协议时，查对应标准。设计新模块或比较重大方案时，研究相关开源实现或论文，
记录具体机制、适用条件和本地选择。资料数量服从问题需要，不要求每次小修改都对比两个项目。

### 第三步：写明模块设计

新模块使用 [设计记录模板](MODULE_DESIGN_RECORD_TEMPLATE.md)。已有模块只更新受影响部分。
至少说明：模块负责哪些状态，接口怎样握手，指令或事务怎样完成，错误与恢复怎样处理，
以及如何验证。

有多个可行方案时，在本检查点选择一个并说明原因。可以先采用容易验证的方案；保留
重新评估的条件，不把所有未来优化提前写成强制要求。

修改寄存器边界、等待或旁路时，按[对应检查表](NAMING_GUIDE.md#寄存器等待与旁路检查)
核对生产者、消费者、反压和错误恢复。风格同步先比较命名归一后的代码标记；涉及平台或
位宽差异的文件逐项适配，不能因为源工程已通过测试就省略目标配置回归。

### 第四步：实现一个可验证的改动

- 控制修改规模，避免同时改变多个难以区分影响的机制；为修正同一接口可一起修改相关模块。
- 教学 TODO 放在准确插入位置上方，让读者能够直接在其下方实现。
- 尚未具备约定行为的新模块留在实验目录，不加入正式构建文件列表（filelist）。
- 接口变化时，同步修改父模块、相关断言、测试和文档。
- 利用 Git 或独立实验构建保留可回退的检查点，不长期维护相互冲突的主线配置。

### 第五步：按改动范围验证

| 改动内容 | 常用检查 |
| --- | --- |
| 文档与注释 | 路径和链接、命令名称、术语、与源码及其他文档的一致性 |
| 命名与结构整理 | 引用完整性、lint，以及能够覆盖改动的已有测试 |
| 局部功能 | lint、定向测试、受影响模块的回归 |
| 请求/响应协议 | 增加反压、可变延迟、错误响应和取消/排空行为检查 |
| 指令或流水线语义 | 模块测试、整核程序、声明范围内的 DiffTest |
| 性能与时序 | 功能回归后，测量相同输入下的周期，运行受影响的综合与时序检查 |

关键控制性质可增加形式验证。必须记录实际命令、证明范围、约束和工具结果，不能因为
目录中有断言或形式验证文件就写“已证明”。端到端程序通过也不能替代局部协议检查。

### 第六步：保存结论

把命令、版本、配置、实际结果和限制追加到 [验证记录](../verification/EXPERIMENT_LOG.md)。
学习到的机制及适用条件可以记入 [学习日志](../learning/LEARNING_JOURNAL.md)。

设计变化时更新当前规范，保留旧实验的原始结果与日期。没有运行的检查写“未运行”，没有
解决的问题写“待处理”，不使用没有范围说明的“全部通过”或“完整支持”。

## 3. 参数与模块组织

1. 当前只维护 `rv64-edge-ai` 构建配置。已有常量和类型不代表对应硬件已经实现。
2. 全核配置由统一入口定义，局部派生宽度在使用它的模块或类型定义处计算。
3. `XLEN`、`INSTR_WIDTH`、`PADDR_WIDTH` 和 `MEM_AXI_DATA_WIDTH` 分别表达整数、指令、
   物理地址和内存总线数据的宽度，不能互相代替。
4. 名称和单位遵循 [命名规范](NAMING_GUIDE.md)；对实际存在的最小值、整除关系和索引边界
   增加构建展开时检查，不对没有该要求的参数强制施加 2 的幂约束。
5. 多路缓存、多 bank 和队列使用数组与 `generate`。增加参数组合时，同时增加对应验证。
6. 每组寄存器或协议状态由明确模块负责更新。端口传递完成本模块工作所需的信息，避免
   读取其他模块内部状态来作决策。
7. 缓存查找、数据阵列、缺失处理和 AXI 适配按职责组织。只有确有独立状态、接口或时序
   需要时才拆分模块，避免仅为追求模块数量而拆分。
8. 仿真监视器、DPI 和存储模型与可综合 RTL 分开；软件可见的架构计数器仍属于硬件。

## 4. 接口必须回答的问题

- 谁给出 `valid`，谁给出 `ready`，哪次握手表示请求被接收？
- 响应什么时候完成，反压时哪些数据和身份字段必须保持稳定？
- 最多有多少个未完成事务，响应按什么顺序返回？
- flush、redirect、异常和复位遇到未完成事务时，谁负责取消、排空或丢弃响应？
- 写内存和 MMIO 等不可撤销操作何时获准发生？
- 错误由谁检测，地址和原因保存在哪里，如何交给使用者处理？
- 若支持同周期传递，下游阻塞时数据保存在何处，是否存在组合环？

已被 AXI 下游接收的事务不能仅靠清空 CPU 流水线取消；清除指令与完成总线事务分别处理。

## 5. 性能记录的口径

每组正式比较至少记录：

- Git commit；若工作区未提交，还要保存补丁或源码快照及其校验值。
- 完整硬件参数、软件版本、编译选项、输入、镜像校验值和随机种子。
- 构建及运行命令，周期数、退休指令数和计数起止范围。
- 本次问题所需的分支、缓存、访存或总线事件；未实现的单元不填写虚构计数。
- 综合与时序结果对应的源码、工具版本、库、约束和存储阵列实现。

比较版本 A 和 B 时，允许 RTL 不同，但要控制其他实验条件。每个版本的周期、面积和时序
分别对应自己的 RTL，不能用 A 的频率解释 B 的周期。改变缓存容量或总线延迟时，应把它
标为实验变量；结果可以比较，但不能把收益归因到未改变的部分。

当前阶段可以只报告实测面积与时序；没有功耗估算或测量时，不填写能耗结果，也不把面积
直接当成能效。更快和更慢的结果都保留。

## 6. 文档怎样写才容易理解

1. 开头先说这份文档解决什么问题，以及是当前要求、当前实现还是未来候选。
2. 区分“必须遵守的正确性规则”“本阶段选择”和“以后可比较的方案”。技术选项没有
   决定时直接写待定，不写成已完成或必需。
3. 使用具体主语和动作，例如“IFU 丢弃旧路径响应”“ROB 队首处理异常”。少用“闭环”
   “赋能”“语义表面”等无法直接指向行为的词。
4. 正文优先使用中文。必要英文术语首次出现时给出简短说明，代码标识保持原名。
5. 一句话尽量只说明一件事；参数比较和状态区分使用表格，步骤使用有序列表。
6. 每个结论注明依据和范围。已有源码、历史测试、当前测试、设计要求和推测分开写。
7. 使用相对链接指向相关文档或源码；历史计划保留原文并加失效说明，避免被当作当前规范。
8. 修改日期表示文档更新时间，测试日期只在真正运行测试后更新。
