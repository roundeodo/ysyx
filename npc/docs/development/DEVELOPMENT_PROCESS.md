# NPC 开发流程与工程方法

状态：已接受

最后更新：2026-07-30

## 1. 目标

本项目不仅交付能够运行的 RTL，还用于学习成熟处理器团队的工程方法。每次开发都必须
同时产生三类结果：

1. 可验证的硬件实现；
2. 可复现的功能与性能证据；
3. 能迁移到下一模块的设计经验。

## 2. 固定开发闭环

### 第一步：定义负载和问题

- 指明模块服务的真实工作负载和系统路径；
- 写出当前瓶颈的计数器证据；
- 给出功能、延迟、吞吐、面积和验证目标；
- 明确本检查点不解决的问题。

### 第二步：研究一手资料

- 至少研究两个相关的开源实现、标准或论文；
- 只记录具体机制和接口契约，不能只记录项目名称；
- 对每项机制写明采用、调整或拒绝及其本地依据。

### 第三步：冻结设计记录

按[`MODULE_DESIGN_RECORD_TEMPLATE.md`](MODULE_DESIGN_RECORD_TEMPLATE.md)记录：

- 所有权边界；
- 参数和合法配置；
- 接口事务与反压规则；
- 数据结构和状态；
- 正确性不变量；
- 时序、快速路径和验证计划。

### 第四步：分检查点实现

- 每个检查点只能改变一个可独立验证的边界；
- TODO 紧邻准确插入位置，并允许直接在其下方实现；
- 未完成模块不进入活动 filelist；
- 父模块、断言、测试和文档与接口修改同时提交。

### 第五步：分层验证

依次执行：lint、模块级定向测试、随机反压/随机延迟、集成回归、DiffTest、软件测试和
性能实验。不能用端到端程序偶然通过替代协议级验证。

### 第六步：记录和评审

- 向实验日志追加 commit、配置、命令、结果和分析；
- 对比修改前后的功能、性能、面积和时序；
- 把有证据支持的结论写入学习日志；
- 设计决策变化时，保留旧记录并增加替代关系。

## 3. 参数化原则

参数化的目标是复用经过验证的结构，不是让任意参数组合都能通过编译。

### 3.1 可以参数化的内容

- `XLEN`、物理地址宽度和总线数据宽度；
- fetch/decode/issue/commit 宽度；
- 队列、ROB、LSQ、MSHR 和物理寄存器数量；
- cache set、way、line bytes 和 bank 数量；
- 分支预测表容量和历史长度；
- 可选功能开关，例如 MMU、Vector、ECC 和预取器。

### 3.2 参数实现规则

1. 基础参数在单一配置入口定义，派生宽度使用 `localparam` 或纯函数计算。
2. 参数单位写入名称，例如 `_bytes`、`_entries`、`_bits`、`_ways`。
3. 所有 2 的幂、整除、最小容量和索引宽度要求都使用 elaboration-time 检查。
4. 多 lane、多 bank 和多 way 使用数组及 `generate`，不能复制带编号的信号和模块实例。
5. 不允许把不同语义的宽度绑定到一个参数；`XLEN`、指令宽度、地址宽度和总线宽度
   必须独立。
6. 参数变化后，类型、循环边界、断言、覆盖点和软件可见配置必须同步变化。

### 3.3 命名配置而非任意组合

维护经过回归的命名配置，例如：

- `YSYX_RV32_BASELINE`：当前课程和功能回归基线；
- `YSYX_RV64_SEQUENTIAL`：RV64 多周期和顺序流水线功能基线；
- `AI_RV64_OOO`：乱序超标量主处理器；
- `AI_RV64_VECTOR`：加入标准向量执行能力的 AI 配置。

CI 和 `make perf-record` 只对命名配置给出可复现承诺。其他参数组合属于开发实验，必须
先通过合法性检查和完整回归，才能成为新配置。

## 4. 模块化原则

1. 一个状态只能有一个架构所有者；top 只连线和选择配置，不能承载散落的功能逻辑。
2. 模块端口传递事务及其元数据，不能依赖其他模块的内部状态。
3. CPU 内部协议、cache refill 协议和 SoC AXI/APB 边界分层，使用 adapter 完成转换。
4. 策略与机制分离。例如替换策略、仲裁策略和预测策略应能在不改主数据通路的情况下替换。
5. 控制路径和数据阵列分离；meta、data、miss/refill 和主流水线分别拥有自己的状态。
6. 仿真模型、性能监控和芯片功能 RTL 分层，综合配置必须能排除仅供仿真的模块。
7. 跨模块共享类型放入 package；只被单模块使用的类型留在模块内部。

## 5. 接口评审

每个接口必须回答：

- 谁产生 `valid`，谁产生 `ready`？
- 哪次握手开始事务，哪次握手结束事务？
- 反压时哪些载荷必须稳定？
- 最多允许多少个未完成事务，响应是否有序？
- redirect、flush、异常和 reset 如何处理在途事务？
- 错误如何返回，地址和原因由谁保存？
- 是否存在合法的同周期旁路，寄存器后备路径是什么？

## 6. 代码评审

- 命名是否能直接表达来源、目的、功能和数据形状；
- 参数是否有单位、派生关系和合法性检查；
- 是否存在隐式位宽截断、符号扩展或数组越界；
- 状态机是否按输出、转移、时序更新的顺序组织；
- 每个信号是否只有一个过程所有者；
- 快速路径是否引入组合环或高扇出；
- 断言是否覆盖丢失、重复、过期响应和反压稳定性；
- 性能事件是否对应真实握手或架构提交，而不是含糊的状态推断。

## 7. 性能实验纪律

每条正式性能记录必须包含：

- Git commit 和工作区是否干净；
- 命名硬件配置和软件 workload；
- 构建、运行和综合命令；
- 主频、周期数、指令数和 IPC；
- cache、TLB、分支、LSU 和总线关键计数器；
- WNS、面积和工具版本；
- 修改前后差异及下一步判断。

不能只保留更好的结果，也不能在缺少解释时把不同配置的数据放在同一张对比表中。
