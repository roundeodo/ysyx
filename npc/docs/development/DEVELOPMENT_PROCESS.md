# NPC 开发流程

已接受，2026-09-16；更新于 2026-09-22。代码要求见[编码规范](NAMING_GUIDE.md)，模块说明使用
[精简模板](MODULE_DESIGN_RECORD_TEMPLATE.md)；这里只规定工作顺序和证据要求。

每次开始 RTL 设计、修改或评审，先阅读本流程、编码规范和相关模块的当前说明，
按[寄存器、等待与旁路检查](NAMING_GUIDE.md#寄存器等待与旁路检查)检查受影响通路。
检查范围随改动确定；修改局部逻辑不要求重写所有模块文档。

## 1. 先确定问题与电路

1. 明确要解决的功能问题或性能瓶颈。优化应有负载和计数器依据，写清预期收益与代价。
2. 先在现有模块说明中确定组合路径、并行支路、反馈、寄存器和状态归属，再开始写 RTL。
   写清每组状态的用途及写入、保持、清除条件；源码顺序应能直接对应这份结构。
3. 新架构或陌生协议查一手资料，记录真正影响选择的机制及依据；普通整理不为凑数量
   增加研究章节。尚未解决且会影响正确性的问题应先明确，不能隐含在代码里。

## 2. 按结构实现

- 按数据流和状态归属组织声明、组合运算与更新；独立反馈路径单独成组。
- 状态机按“组合输出 → 下一状态 → 时序更新”书写；具体排版与命名遵守编码规范。
- 分成可独立验证的改动。接口变化时同步修改父模块、类型、断言、测试和当前说明。
- 参数从统一配置入口传入；派生宽度、数组、循环边界和合法性检查随之变化。
  只对已验证的命名配置作功能承诺，新增并发度或执行能力需要对应的真实实现。
- 不把功能状态、策略或协议转换散放到只应负责接线的顶层。
- 编码完成后沿实际连接复查一次：核对新增/保留状态的理由、已满足条件下的等待、
  旧新事务交接和源码冗余；本轮新增的旁路与保留的等待分别说明依据。

## 3. 验证改动

按受影响的边界选择检查，不机械重复全部流程：

| 改动 | 必要检查 |
| --- | --- |
| 纯说明、排版 | 链接与内容一致性；RTL 排版还需语法和词法比较 |
| 独立声明或过程块移位 | 检查作用域和每块内容不变，lint 与相关模块回归 |
| 数据通路、状态机、接口变化 | 定向测试、断言、随机反压/延迟；影响整核行为时加 DiffTest 与软件回归 |
| 性能或寄存器边界变化 | 同配置负载周期数、面积和 STA，按通过时序的频率比较执行时间 |

请求不能丢失、重复或错配；valid 被反压时载荷稳定；flush、复位和错误的处理必须明确。
端到端程序通过不能替代这些接口检查。未运行的检查明确标注，不推断为通过。
优化按“现状测量 → 单项候选 → 正确性验证 → 同条件收益比较”推进；没有收益证据的
候选不写成已完成优化。计时器频率、设备延迟和软件计时窗口的变化须与硬件收益分开。

## 4. 维护说明与证据

- 模块说明只保留当前原理、电路结构、工作过程和关键取舍。内容直接更新，不把每次
  修改过程不断追加在末尾；重复说明改为链接，不适用的章节和空表省略。
- 验证记录保存版本、工作区差异、配置、命令、结果与原始证据；实验日志只留简短索引。
- 性能记录必须说明负载、主频、计时窗口、周期/退休数、IPC及对应面积、时序口径。
  不混用不同配置，不覆盖旧结果，也不只保留较好的测量。
- 需要追溯的旧方案归档并标明替代关系，不作为当前实现依据。
  学习日志只记录新的、可复用且有证据的结论，不要求每次小修改都新增条目。

研究型探索须同步维护可供后续学习的设计依据记录，而非只留下最终方案：

- 给出论文和作者项目入口、年份/版本、原系统前提；区分初筛、已阅读、模型、RTL 和已验证采用。
- 记录问题证据、可检验假设、简单对照、借鉴与改造边界，以及新增状态、接口和时序成本。
- 将采用/拒绝原因链接到实际实验；保留负结果、退化场景、测量修正和未完成项。
- 模块说明保持简洁；学习记录解释取舍，完整数值、命令与日志由验证记录唯一维护。
  可参照[前端研究学习记录](../learning/FRONTEND_RESEARCH_NOTES.md)，不要求每次小修改另建文档。
