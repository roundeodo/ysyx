## 2. 优先修复的功能错误

### F1：D-cache 响应被阻塞时，未接收的输入地址会改变返回数据

位置：[riscv_dcache.sv](../../vsrc/riscv/core/memory/riscv_dcache.sv)，430～443、479～522 行；
[数据阵列](../../vsrc/riscv/core/memory/riscv_dcache_data_array.sv)，31～40 行。

复现步骤：先缓存地址 A；再次读取 A，在命中响应出现后保持 `response_ready=0`；请求已经
接收，此时撤下 `request_valid`，把输入地址改为同一行的下一个数据字。下一拍响应仍有效，
返回值却从 `5d5c5f5e59585b5a` 变成 `5554575651505352`。

原因是 S1 请求身份只在握手时更新，而 tag/data 阵列仍逐拍读取外部输入地址。响应直接
使用阵列输出，未被接受的新地址因此改变了旧请求的数据。输入无效时不应要求上游保持
地址来维持已经产生的响应。

当前 LSU 在等待响应时保留请求上下文，普通整核访问可能掩盖这一问题。缓存自身的请求、
响应接口仍有缺陷，未来修改 LSU 周转或复用缓存时会暴露。

修复要求：让阵列输出与待完成请求保持对应，或单独保存被阻塞的响应。不能只冻结 S1
身份。若选择冻结阵列读取，还需检查 store 到下一次 load 的旁路数据是否保持到消费完成。

验收至少覆盖：响应连续反压、无效输入地址变化、有效但未握手的下一请求、跨字与跨组地址、
相邻 store/load 的不同字节掩码，以及反压解除后的连续请求。

### F2：脏行写回失败后，缓存继续服务请求，但此前写入的数据无法恢复

位置：[riscv_dcache_miss_unit.sv](../../vsrc/riscv/core/memory/riscv_dcache_miss_unit.sv)，
213～225、324～379 行。

复现步骤：把 A 写成 `8877665544332211`，访问同组冲突地址使 A 成为替换行；让下层拒绝
该次写回并返回错误。当前缺失请求收到访问错误后，再读 A，得到旧内存内容
`5d5c5f5e59585b5a`，此前已完成的 store 数据丢失。

普通缺失在发起写回后立即使旧行无效，并允许新行回填覆盖原数据路；它不等待 B 响应。
最后确实检查了写回与回填错误，也不会把失败的新行安装为有效行，但返回错误后直接回到
空闲态，没有恢复旧脏行、重试或阻止后续正常访问的流程。

`victim_line_data_q` 此时可能仍保留旧数据副本，所以问题并非“所有寄存器都已丢掉数据”，
而是该副本没有继续承担可恢复脏数据的职责，之后还能被下一次事务覆盖。

写回与回填并行本身可以保留。需要明确：在写回成功前由谁保管脏数据，失败时如何恢复或
重试，以及无法恢复时如何停止正常服务并报告系统错误。简单方案也可以先等待写回成功
再覆盖旧行；采用哪种方案应作为独立行为修改记录，不能仅给当前请求返回 fault 就算完成。

验收至少覆盖：B 错误早于、晚于、同拍于最后一个 R；R 错误；双向错误；错误响应反压；
错误后旧地址再访问及再次冲突替换。`fence.i` 清理错误还需另做整核验证。

## 3. 旁路检查：已有路径与值得评估的路径

旁路应解决明确的数据等待或气泡，同时说明阻塞时在哪里保存数据、冲突时选谁，以及是否
延长组合路径。下面的候选没有性能测量，不能直接写成已经能提高 IPC。

| 路径 | 当前实现 | 判断与下一步 |
| --- | --- | --- |
| WB → 读寄存器级新输入 | core 在捕获前选择同拍写回值 | 已有，解决寄存器同拍读写语义 |
| WB → 读寄存器级被阻塞的数据包 | register_read_stage 监听 WB，更新尚未向下游传递的操作数 | 已有，避免停顿期间错过写回；与上一项作用周期不同 |
| EX、EX/MEM、WB → ID/EX 操作数 | hazard controller 按最近生产者优先选择，core 完成数据选择 | 已有；重复出现 WB 比较不等于重复功能 |
| D-cache store → 相邻 load/缺失判断 | 按字节合并数据，并前递同组脏位 | 已有；修改 F1 时必须保留这两类效果 |
| D-cache 写请求 → AXI AW/W | 行适配器空闲时直接给出首拍，之后保存事务继续发送 | 已有首拍直通 |
| D-cache 脏行收集 | 第一次同步读后，每拍捕获当前字并预读下一字 | 已有连续读取，不是每个字都多空转一拍 |
| D-cache 写回 → 新行回填 | 普通缺失允许 B 尚未返回时启动 AR/R | 已有并行；当前问题是 F2 的失败恢复 |
| BTB 待写更新 → 后续训练 | 训练快照会选择 pending update 中的最新表项 | 已有，防止连续训练使用过期状态 |
| BTB 待写更新 → 查询 | 查询快照仍从表阵列读取，同拍写入不能自动成为本拍快照 | 可评估查询旁路；属于预测质量与时序取舍，不是指令功能错误 |
| I-cache 已回填字 → 新查询 | 存在选择信号，但请求接收条件把它挡住 | 见下方 C1，先清楚区分现用逻辑与候选实现 |
| load 结果 → 后继相关指令 | 当前等待 WB 才前递 load，LSU busy 阻止执行级继续前进 | 可评估更早前递；需明确响应保存、访问错误与组合路径 |
| LSU 完成旧请求 → 接收新请求 | 当前 IDLE、DISPATCH、WAIT_RESPONSE 分阶段，没有完成拍接收下一条 | 是连续访存的优化候选；须连同流水停顿和提交顺序检查 |
| 取指缓冲、ID/EX 空队列直通 | 缓冲保留寄存器边界，ready 不直接跟随下游 ready | 有意控制组合路径；不能仅凭多一级就判设计错误 |

### C1：I-cache 留有不能启用的回填字选择路径

在 [I-cache](../../vsrc/riscv/core/frontend/riscv_icache.sv) 234、387、451 行，接收新查询要求
`!miss_transaction_present`，但 `lookup_uses_refill_word_s1_d` 只有在接收新查询且
`miss_transaction_present` 时才可能置一。这两个条件互斥；复位后该标志不能置一，
对应的 S1 回填字命中选择路径不可达。

这不否定当前“原缺失请求所需字到达后提前返回”的功能，两者是不同路径。可以先移除或
隔离这部分候选逻辑；若要启用，则必须设计新请求与原缺失响应的顺序、同路阵列读写冲突、
失效和反压处理。不能仅放宽 ready 条件就认为完成 hit-under-miss。

### C2：还有明确的带宽限制，但需要测量后再优化

- I-cache 在 64 位 AXI 上按 4 B 取指字回填，64 B 行需要 16 次数据传输；D-cache 当前
  按 8 B 传输。I-cache 可评估按 8 B 接收并拆成两个指令字，但这涉及回填缓冲和阵列写口，
  不能只改 AXI size，也不能据此推算 IPC 翻倍。
- AXI 合并器一次只允许一个未完成读突发；最后一拍 R 完成前不会发出下一次 AR。
  可评估事务周转，但当前主要瓶颈还可能在上游 LSU 和流水停顿。
- 两槽缓冲满时，即使下游当拍取走一个，也不能同时接收新输入；这是 ready 只依赖
  本级状态的代价。非满状态仍可连续传递，不能笼统写成“每两拍才能走一条”。

## 4. 难读、难维护与重复代码

| 位置 | 具体问题 | 建议 |
| --- | --- | --- |
| core | 全局声明较长；操作数选择、缓存维护、恢复和仿真观察分散 | 先按功能把声明与计算放近，再评估独立的操作数选择或维护控制模块 |
| 预测器 | 查询、训练快照、延迟写入、BHT/BTB/RAS 更新交错；注释容易让人误认已有查询旁路 | 按状态负责的功能组织代码，明确训练旁路与查询旧值行为 |
| D-cache | 423 行仍说 store 后停一拍，463 行却说明已取消该气泡 | 更正过期注释，并把 F1 的阵列读出身份约束写在读口控制旁 |
| D-cache 与 miss unit | `merge_store_bytes()` 两份实现相同 | 可抽成缓存共用纯函数，减少修改遗漏；这不是重复硬件面积的证据 |
| LSU | `request_has_memory_access()` 定义后没有调用 | 删除无用函数，避免读者误认它参与访问资格判断 |
| 预测器与 IFU | 预测器计算 `lookup_next_pc_o`，core 将该端口留空，IFU 再按方向与目标计算 next PC | 统一由一处负责；未连接输出可能被综合删除，不能声称存在双份加法器面积 |
| 公共 riscv_pkg | 当前顺序流水类型与未来 ROB、物理寄存器等类型混在一个大包中 | 按依赖关系分组，必要时再拆包；未来类型不等于已实现硬件 |
| sim/top 与 riscv_npc_axi | DPI 提交 PC 观察逻辑重复维护 | 建立一致的提交观察记录；先核对采样时序并定位现有 csr-trap 比对失败，再合并重复代码 |
| redirect_arbiter、axi4_error_target | 在 filelist 中，但当前顶层没有实例化使用 | 标明保留原因，或独立移入实验区/删除；未实例化不等于占用硬件面积 |
| 仿真性能监视器 | 原始事件统计、推算上限和展示代码集中在长模块 | 分组原始计数和推算方法，让读者能区分实测与估算 |

以下结构不应因外观重复而机械改写：大译码 case；CSR 中具有共同优先级的相关寄存器更新；
RV64 全宽运算与 W 指令的不同宽度、符号扩展处理；各流水边界上负责不同周期的前递。
I-cache 数据阵列含显式锁存器，其存储语义也不能用普通组合逻辑的默认赋值规则替换。

后续整理继续采用 [命名与代码组织规范](../development/NAMING_GUIDE.md)：名称描述含义与
数据形状，局部声明紧邻对应功能，状态机按输出、下一值、寄存器更新排列，注释说明约束
和原因。把一个大 always 拆成许多远离声明的小 always，并不会自动提高可读性。
