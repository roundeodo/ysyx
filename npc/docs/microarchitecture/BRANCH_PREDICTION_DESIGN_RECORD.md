# 分支预测设计与Branchsim探索记录

## 1. 目标与边界

当前顺序流水线已经实现JAL目标预译码和16项、2-bit饱和计数器BHT，但JALR仍在EX级
解析。这个检查点能验证预测、纠错和精确提交闭环，不是面向本地AI Agent的最终前端。

本地AI工作负载同时包含两类控制流：矩阵内核中的规则循环，以及runtime、算子调度、
内存管理和系统软件中的间接调用与返回。只优化条件分支方向不能覆盖后者，因此本次探索
把方向预测、间接目标预测和返回预测分开统计。

## 2. Branchsim输入与职责

NEMU按架构顺序执行程序，并为每条已退休控制流记录以下信息：

- 该指令在退休指令流中的序号；
- 控制流指令PC；
- 真实下一PC；
- 32-bit指令编码。

Branchsim从指令编码区分条件分支、JAL和JALR，从真实下一PC得到实际方向或目标。它不读取
NEMU内部预测器状态，也不模拟错误路径，因此可以快速比较：

- `sequential`：所有控制流均按顺序PC执行；
- `btfnt`：后向条件分支预测跳转、前向条件分支预测不跳，JAL直接预测；
- `bimodal`：PC索引的2-bit饱和计数器，JAL直接预测；
- `gshare`：PC与全局历史异或索引2-bit计数器，JAL直接预测；
- direct-mapped BTB：保存JALR的PC tag和动态目标；
- RAS：按RISC-V的x1/x5链接寄存器提示维护返回地址。

方向错误、JAL错误和JALR目标错误分别统计。总准确率的分母是全部控制流指令，MPKI的
分母是全部退休指令。

## 3. MicroBench test首轮结果

本次trace包含727206条退休指令和193720条控制流，其中条件分支174315条、JAL 8280条、
JALR 11125条。结果包含启动和测试框架，适合作为首轮筛选；最终RTL决策还需要使用train
规模和AI runtime代表性trace复核。

| 方案 | 预测错误 | MPKI | 5级单发射理想IPC | 存储位估算 |
| --- | ---: | ---: | ---: | ---: |
| 顺序取指 | 169724 | 233.392 | 0.6818 | 0 |
| BTFNT + JAL | 22401 | 30.804 | 0.9420 | 0 |
| 16项bimodal + JAL，当前RTL方向结构 | 16077 | 22.108 | 0.9577 | 32 |
| 64项bimodal + JAL | 15923 | 21.896 | 0.9580 | 128 |
| 64项bimodal + RAS8 | 12196 | 16.771 | 0.9675 | 388 |
| 64项bimodal + BTB32 + RAS8 | 10430 | 14.343 | 0.9721 | 2180 |
| gshare256/history4 + BTB32 + RAS8 | 9705 | 13.346 | 0.9740 | 2568 |

存储位只统计预测状态、BTB tag/target和RAS内容，不代表综合面积。组合索引、比较器、读端口、
时序旁路和布线必须通过综合与STA重新评估。

## 4. 结果解释

当前16项bimodal的条件分支方向错误为4952次，但没有目标预测时，11125条JALR全部产生
预测错误。把BHT从16项扩大到64项只减少154次错误；加入RAS8则利用call/return结构减少
约3727次返回错误。BTB32与RAS8结合后，JALR目标错误降到5632次。

BTB从32项扩大到64、128项没有继续改善本次结果，256项也只额外减少1次错误。这说明剩余
JALR错误主要来自冷启动、同一JALR指令的动态目标变化或当前直接映射目标模型无法利用的
上下文，而不是简单容量不足。继续扩大BTB不具备合理收益。

gshare256/history4把条件分支错误从当前结构的4952次降到4073次。history6和history8反而
更差，说明本trace中更长全局历史引入了额外训练稀释或别名；不能依据“历史更长”直接判断
预测更好。

## 5. RTL取舍与实施顺序

当前RTL已经实现16项两位饱和BHT、JAL立即数目标预测和4项RAS。MicroBench实测中，EX纠错
由34634次条件分支和7455次JALR组成，JAL纠错为0。RAS4到RAS8只额外减少250次错误，却
增加129位返回地址状态及更深选择逻辑，因此保留RAS4。BHT16扩大到BHT64只减少约1320次
错误；按当前约6拍恢复代价估算，对总周期的理想收益不足1%，现阶段不扩容。

下一阶段不是在响应侧继续堆表项，而是把预测提前到取指请求侧：

1. 加入小型next-line predictor/BTB，在发出I-cache lookup时同时形成下一取指地址；
2. IFU允许至少两个带tag和epoch的lookup在途，使I-cache命中流水线可以持续每拍接收请求；
3. fetch queue按frontend tag选择性丢弃错误预测之后的年轻项，而不是无条件清空全部内容；
4. EX只负责校验方向和目标并训练预测器，错误时通过既有redirect边界恢复；
5. 若以后采用gshare或更强的推测历史预测器，必须在FTQ保存历史检查点并在redirect时恢复；
6. 每次扩展必须同时比较RTL纠错次数、`IPC * Fmax`和综合面积，Branchsim只用于候选筛选。

该顺序的原因是当前STA关键路径已经穿过“命中响应、译码/预测、下一PC选择、下一次I-cache
请求”。只增大响应侧BHT既不能切断该路径，也不能让前端拥有多个在途请求。

面向未来乱序多发射设计，预测器还需要FTQ级历史检查点、更高带宽BTB、间接分支上下文预测
以及更强的方向预测器。是否采用TAGE类结构必须由AI workload trace、面积和时序数据决定，
不能直接替换当前检查点。

## 6. 模型限制

Branchsim只处理退休路径，不包含错误路径对BHT、BTB和I-cache造成的污染，也不模拟多条在途
分支之间的训练延迟。它给出的IPC只包含理想发射周期和错误预测恢复周期，不包含I-cache、
D-cache、LSU结构冲突、RAW等待和前端带宽。因此它用于设计空间筛选，不替代RTL性能仿真。
