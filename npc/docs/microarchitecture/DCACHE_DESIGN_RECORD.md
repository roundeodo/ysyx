# D-cache 设计记录

状态：当前结构说明；验证范围见实验记录

最后更新：2026-09-25

## 1. 当前结构与职责

D-cache 保存数据访问使用的缓存行。当前为组相联、阻塞式 L1 数据缓存，默认 256 B、2 路、
16 B 缓存行。写策略为 write-back/write-allocate：写命中先修改缓存并标记为脏；写缺失
读取目标行，在回填目标数据字时合并写入内容；脏行被替换或显式维护时写回下层内存。

| 模块 | 负责什么 |
| --- | --- |
| `riscv_data_mem` | 根据地址属性选择 D-cache 或 uncached 路径，并输出一个数据侧 AXI 接口 |
| `riscv_dcache` | 缓存查找、命中处理、替换选择和脏行维护 |
| `riscv_dcache_tag_array` | 保存标记、有效状态与脏状态 |
| `riscv_dcache_data_array` | 同步读数据，按字节写使能更新数据 |
| `riscv_dcache_miss_unit` | 执行替换行写回和新行回填 |
| `riscv_dcache_axi` | 将整行读写转换成 AXI4 突发事务 |

LSU 负责 load/store 的地址、大小和数据格式，不直接操作缓存状态或 AXI 通道。

容量、相联度和行大小与 RV32 最终预设一致；核内数据及 AXI 数据仍为 64 位。
当前为 8 组，每行含 2 个 64 位字。配置及风格同步的验证见
[本轮记录](../verification/DCACHE_STYLE_SYNC_2026-09-25.md)。

## 2. 查找与命中

S0 接收 `data_memory_req_t` 并启动同步阵列读取。S1 用保存的请求与阵列输出判断命中。

- load 命中：返回所在数据字，LSU 根据访问大小和符号属性提取结果。
- store 命中：按 byte strobe 指定的字节合并数据，并设置脏位。
- 命中响应与下一次查找可同拍交接；紧邻的同字写读通过字节旁路取得更新值，不依赖 SRAM 同地址读写行为。

缺失或脏行维护期间，缓存不接收新查找。当前不支持 hit-under-miss，即不能在一条缺失
尚未完成时继续服务其他命中请求。

阵列只在接收新查找或执行内部维护读取时更新读出结果。S1被阻塞时，请求身份、阵列
输出和相邻store的旁路一起保持，未接收的输入地址不能改变响应。该规则修复了
[先前检查中的 F1](../architecture/RTL_DESIGN_REVIEW.md)。

## 3. 缺失处理

先选择无效路；没有无效路时使用每组轮转指针选择替换行。

1. 替换行有效且为脏时，把该行读入写回缓冲并发起 AXI 写突发。第一次同步读取后，
   每拍捕获一个数据字，同时预读下一字。最后一个字直接与已有缓冲拼成写回请求，
   不再为收集结束单独等待一拍；请求被反压时保留完整行。
2. 普通缺失在写回请求被接收后立即使旧行无效、发起新行回填，允许 AR/R 与尚未完成
   的写回事务重叠。维护操作则等待 B 响应成功后才清除脏位。
3. 回填数据直接写入所选路。原请求为 store 时，在目标字到达时按 byte strobe 合并；
   所需数据字另外保存，用于最终响应。
4. 整行回填与所需写回均成功后，安装新标记和有效位；store 缺失安装为脏行，load 缺失
   安装为干净行。最后一个必要响应到达时可同拍安装并返回结果，反压时才保留响应；
   不另发一次查找重放。
5. 回填失败时不安装新有效行。写回失败时，先排空读写事务，再把已有写回缓冲逐字恢复
   到原路，恢复旧tag、有效位和脏位，最后向当前请求返回错误。之后仍能重读或重试写回旧行。

写回缓冲只在 miss unit 中保存一份。`dcache_writeback_req_t` 只携带行地址和事务号，
整行数据通过 `writeback_line_data` 单独连接到 AXI 适配器。从写回请求握手到响应握手，
miss unit 必须保持这份数据；若写回失败，还要保持到旧行恢复完成。适配器只保存地址与
传输进度，不重复保存整行。默认 16 B 行因此少用一份 128 位寄存器缓冲。

这个接口明确区分了“请求已接收”与“数据缓冲可以复用”。普通valid/ready请求内容可以
在握手后改变，但这里单独的数据端口有更长的保持要求，适配器断言会检查。该设计同时
保留正常写回/回填并行，并修复[先前检查中的 F2](../architecture/RTL_DESIGN_REVIEW.md)。

AXI 写地址和写数据独立握手，不能假设二者同拍完成。默认 16 B 行在当前数据侧 8 B
传输配置下需要 2 个 beat，与 I-cache 的 4 B 窄传输不同。

## 4. 脏行维护与 `fence.i`

`clean_req_i` 请求遍历缓存，将脏行写回。每行成功写回后清除其脏位；维护结束时由
`clean_done_o` 报告，并通过 `clean_access_fault_o` 表示是否出错。

正常路径下，core 在 `fence.i` 提交后先排空已呈现的取指，再等待 D-cache 维护、使 I-cache 失效，确保后续
取指能够看到已经写入内存的新指令。

`riscv_fence_i_ctrl` 负责维护次序。清理失败时，失败行仍保持dirty；
控制器保持取指阻塞，将clean请求撤下一拍后重新清理。只有清理成功才启动I-cache失效，
失效完成后才恢复取指。持续总线错误会持续阻塞，当前没有软件可见的机器检查异常或重试
上限；系统级错误报告策略随后续平台设计确定。

## 5. 与其他访问共享内存

数据存储子系统在请求接收时选定路径，并保持到对应响应完成。不可缓存的设备或普通内存
访问走 uncached 路径；不允许的访问在本地返回错误。uncached 成功响应被接收时可以
同拍交接下一请求。响应按旧事务归属返回，新 AXI 请求按当前有效通道选择，二者不能混用。

I-cache 输出指令侧 AXI 请求，数据存储子系统输出数据侧 AXI 请求，系统层再仲裁两侧。
当前共享读通路最多一个未完成读突发，见 [互连说明](../interconnect/AXI4_ARCHITECTURE.md)。

## 6. 必须检查的性质

- 标记、有效位、脏位和数据更新保持一致。
- 成功写回之前必须保留可恢复的脏数据；若提前覆盖阵列，缓冲必须继续负责保存并恢复
  旧数据。当前实现先恢复旧行再报告错误；回填失败不能安装有效行。
- store 只能更新字节使能选中的内容。
- 一次请求只返回一次响应，反压时保留响应内容和身份。
- uncached 请求不修改缓存元数据，设备访问不能因错误路径执行产生副作用。
- 维护出错时保留或处置脏数据的规则明确，并有整核错误注入测试。

实际测试结果见 [验证记录](../verification/EXPERIMENT_LOG.md)。

## 7. 后续工作

持续回归响应反压、相邻写读、B/R完成顺序与错误恢复，测量 load/store、缺失和脏行写回
开销。代码整理与测量结果见 [本轮实现记录](../architecture/RTL_CLEANUP_RECORD.md)。

M2 首先解决访存指令的年龄、队列和 store 授权，可以保留阻塞式缓存。以后按实际瓶颈
评估独立写缓冲、store 队列到 load 的数据前递、多 MSHR、SRAM 宏和分 bank。当前缓存
已经有相邻写读旁路和普通缺失的写回/回填并行，后续优化应以此为起点。

DTLB 随地址转换设计；共享缓存、一致性和 DMA 数据共享随系统阶段设计。它们不要求在
第一版顺序核或乱序核中全部实现。

## 2026-09-26：响应载荷提前准备

miss 单元根据寄存的事务上下文和当前总线数据预先准备响应字、事务 ID 与错误状态，
不等待最后响应的 valid 才选择载荷。D-cache 顶层用已有 miss 占用状态选择响应来源。
响应 valid、握手、错误记账、victim 恢复和元数据安装仍按原条件发生；无有效响应时，
载荷没有交付含义。保持最后必要响应当拍完成，以及新请求同拍交接，不增加寄存器。

对完整 miss 单元进行顺序等价检查：仅在 response valid 为零时屏蔽响应载荷，其他
输出、状态转移与副作用逐项比较，1401 个等价点全部证明。顶层断言检查本地响应与
miss 的所有权互斥。功能与时序测量见[接入验证](../verification/EXU_INTEGRATION_2026-09-26.md)。
