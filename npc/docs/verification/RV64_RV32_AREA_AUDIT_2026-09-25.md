# RV64 相对 RV32 的剩余面积差额

2026-09-25。分析当前 RV64 面积为什么仍高于 RV32，以及哪些开销不应被直接认定为 RV64 必需。

当前比较为 RV64 **124,259.772 µm²**、RV32 **101,617.852 µm²**，
差 **22,641.920 µm²，增加 22.28%**。加宽寄存器和数据通路能解释其中相当一部分，
但预测目标的存储方式仍有明确优化空间，不能把全部差额视为 ISA 的固定成本。

本轮没有修改正式 RTL 或综合默认值。当前已通过 700 MHz 验收的 RV64 网表保持不变。

## 比较范围与复现

两边都是纯核加实际复位控制器；不包含 CLINT、SoC 互连或 AXI64/32 平台转换器。
I-cache 均为 1 KiB/4 路/32 B 行/策略 13；D-cache 均为 256 B/2 路/16 B 行；
BHT16、BTB16 两路、RAS4。物理地址和指令宽度均为 32 位。

标准单元库为 Nangate45 typical，映射使用 AREA 3、820 MHz 目标。这里的面积是标准单元面积，
不包括布局布线留白、时钟树及实际布线寄生后的修复。

RV32 参考为 `branch-followup-20260923/evidence/ppa/B0current`。本轮按其 SHA-256 恢复全部综合源码，
核对 Yosys、主综合脚本、公共脚本和 Liberty，再重新完成映射。原始映射面积为
**101,528.476 µm²**。逐类型单元数量与历史发布值只差历史后处理新增的
48 个 BUF_X4（89.376 µm²），从而将重建网表与 101,617.852 的历史结果对应起来。
诊断脚本仅在 ABC 前增加 JSON 导出，没有增加或删除综合变换。

RV64 使用[缓冲精简记录](BUFFER_AREA_REDUCTION_2026-09-25.md)对应的已验收网表，本轮重新核对
源码绑定与单元面积，没有重跑 RV64 全核综合或 STA。

RV32 历史结果只做复位缓冲处理；RV64 当前结果还包含全网电容修复并通过转换时间检查。
因此把后处理单独列出；不能把本表说成两边刚刚完成了相同的完整电气验收。
RV32 还包含机器定时器中断路径，而当前 RV64 中断尚未接通，比较并非只改变一个 XLEN 参数。

## 哪些增加有明确理由

### 通用寄存器与数据运算

当前 x1～x31 各保存 64 位，而 RV32 各保存 32 位。实际存储从 992 个 DFF 增至 1,984 个，
多 992 个；按当前 DFF_X1 单元，仅存储增加 **4,485.824 µm²**。两个组合读口的数据选择、
写入数据通路及其驱动也变宽，所以寄存器堆的总增量大于这个数。

RV64 的寄存器状态、64 位整数运算、LD/SD，以及 W 类指令的 32 位运算与符号扩展必须有正确行为。
[RV64I 规范](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv64.html)规定这些语义，
并不规定必须使用两套独立 ALU。保持当前单周期执行和吞吐目标时，加宽 ALU、前递及数据寄存级
有合理成本；若复用更窄运算器分多拍执行，须同时报告延迟和吞吐的变化。

### 流水线、CSR 与访存数据

全核 DFF 数量为 8,316 → 10,895，多 2,579 个，实际触发器面积增加 11,767.574 µm²。
除了通用寄存器，部分可直接对应到信号组的变化如下；本表列存储位数，不是含组合逻辑的模块面积。

| 实际寄存数据组 | RV32 位数 | RV64 位数 | 增量 |
| --- | ---: | ---: | ---: |
| BTB 表项，不含有效位和替换状态 | 976 | 1,488 | 512 |
| ID/EX 执行载荷 `execute_packet` | 300 | 428 | 128 |
| 提交数据 `commit` | 183 | 311 | 128 |
| 已寄存执行结果 `resolved_execute_result` | 162 | 258 | 96 |
| D-cache 两路读出数据 | 64 | 128 | 64 |
| IFU 队列中的预测记录 | 66 | 130 | 64 |
| 取指缓冲数据 | 196 | 260 | 64 |
| uncached 请求上下文 | 70 | 106 | 36 |
| D-cache S1 请求记录 | 68 | 103 | 35 |
| D-cache miss 请求记录 | 70 | 105 | 35 |

立即数的符号扩展、恒零字段以及相同来源的部分位已被综合器缩减；不能用整个 struct 声明位数
相减来代替实际触发器统计。也不能把上表所有预测字段都归为架构必需。

`mscratch` 必须保存 MXLEN 位；`mepc`、`mtvec` 等地址类 CSR 则有规范允许的 WARL 约束，
物理状态是否需要完整 64 位取决于实现支持的地址范围。当前实现保存宽地址，不能把所有 CSR
高位都说成不可优化。[机器态 CSR 规范](https://docs.riscv.org/reference/isa/v20260120/priv/machine.html)
分别规定了这些寄存器的要求。软件可见 CSR 的访问宽度与内部真正保存的状态位数应分开处理。

### 缓存容量没有增加

- I-cache 数据阵列两边均为 8,192 个锁存器，标签存储均为 768 个触发器。
- D-cache 数据阵列两边均为 2,048 个触发器，标签存储均为 400 个触发器。
- `mcycle`、`minstret` 两边原本就是 64 位，没有因为 RV64 再翻倍。
- RAS 声明虽然随 XLEN 加宽，实际地址存储只有 128 → 132 位，并没有增加 128 个触发器。

D-cache 和 uncached 通路的读出字、store 数据、字节使能和 AXI 数据拍变宽，会增加外围逻辑。
64 位缓存/总线口是当前减少访问拍数的性能选择，不是 RV64 ISA 强制的总线宽度。改回 32 位口
需要处理 LD/SD 的拆分与合并，不能只改一个宽度常量而保持所有协议和吞吐结论。

## 已发现的优先优化项：预测目标存储

BTB 在当前整核中仍保存每项 64 位目标，共 16 项。其 tag 高位已因训练 PC 的实际来源而被综合为常量，
所以不能再把标签也算成增加 32 位。真实多出的 512 个 DFF 来自目标存储，单元面积为 **2,315.264 µm²**，
此外还有相应的读出选择与驱动。

预测信息不是架构寄存器。对于当前地址范围，可以研究只保存可表示的目标：超出表示范围的目标
不进入 BTB，执行端仍用完整地址完成运算和恢复。还可研究压缩编码，查询时恢复需要的目标位。
不能直接截断整个处理器的 PC、AGU 结果或异常地址。

为检查这是否只有存储位数上的潜力，本轮生成了两份独立 BTB 对照：查询 PC 仍为 64 位，训练 PC
按当前整核条件零扩展自 32 位；表项数、路数、替换策略、工具和映射设置相同。

| 独立 BTB 方案 | DFF 数量 | 单元面积 µm² |
| --- | ---: | ---: |
| 保留 64 位目标 | 1512 | 11,355.806 |
| 保存 32 位目标，高位非零时不训练 | 1000 | 8,060.864 |

独立模块减少 **3,294.942 µm²**。这是本轮实际综合结果，但不是当前整核已经实现的节省值。
独立边界、共享逻辑、驱动优化和约束传播均会影响全核结果；本轮未替换正式 BTB、未做该候选的
整核 DiffTest/性能对照/700 MHz 完整 STA，也没有证明候选在所有地址输入下与旧预测序列相同。
超范围时放弃预测本来就会改变预测序列，最终要验证的是正确执行、恢复行为及性能。

外围预测记录仍有多个 64 位目标字段，后续可沿真实数据流统一检查是否能传递压缩表示。
这部分尚未测量节省值，不能与独立 BTB 收益直接相加。

地址处理还需同步核对：当前 IFU 和 LSU 转为物理地址时使用低 32 位，未见独立的高位范围检查。
缩减内部记录之前，应明确高位地址的别名/报错约定，并验证边界跳转、异常记录及恢复；不能用类型
截断隐含决定这些行为。本轮没有改变这一既有行为，也没有将现有回归写成覆盖了所有高位地址。

## 后续顺序

1. 优先完成预测目标压缩的整核对照，保持 BTB/BHT/RAS 容量，检查正常目标、超范围目标、反压与恢复。
2. 核对预测元数据经过的各个寄存级，去掉不必完整保存的高位或改为可恢复编码；保留真实目标的全宽检查。
3. 再比较 ALU/W 运算的共享方案。源码出现两条运算表达式不等于网表必然有两套电路；以映射结果和时序为准。
4. 最后评估更窄缓存/总线口等会改变访问拍数的方案，收益必须与延迟、吞吐及软件运行周期一起报告。
