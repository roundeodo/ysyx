## 计数结论

用户 RV64IM train 归档：`result/performance/soc-20260927T043307177887Z`。
当前 cpu.cpp、perf_observer.cpp、riscv_perf_dpi.svh、riscv_core.sv、axi4_delayer.v
SHA256 与归档一致。没有运行新的 train。

`riscv_core` 的退休事件为 `commit_valid && !commit.trap_taken`；DPI bit0 传给宿主，
宿主每周期只累加一次该位，同时周期计数加一。计时器读在上升沿前记录当时的周期和累计
退休数，确认该 load 成功提交后输出样本。脚本使用十组原生计分边界分别取差并求和，
不是平均十个 IPC，不将 decoded instructions 当作退休数，也没有把周期再乘七。

独立重算原始 timer-events：71,090,721 条 / 494,678,053 拍 = 0.14371108758285664。
700 MHz 下 0.7066829328571429 s；十段定时器时间之和 0.706685 s。
每个子项的误差均小于 1 us。整次 RTL 与宿主退休数均为 80,482,375；
主机周期 551,662,277 与活跃核周期 551,662,265 相差 12 拍复位/计数边界。
这些交叉检查支持计数链路一致，不能单独证明设备时间建模正确。

逐项原始边界与计数：`result/verification/ipc-audit-20260927/count-audit.json`。

## 时间接近而 IPC 不同

`result/verification/ipc-audit-20260927/rv32-train-20260922-recovered-report.json`。

完整提取文本保存在同目录 rv32-original-report-tool-output.txt；没有重跑或重建旧成绩。

旧 CPU 频率已确认 720 MHz；Scored 为 186,810,327 条 / 522,916,178 拍，
IPC 0.3572471743262837，原生时间 0.726274 s。
Total 为 266,828,424 条 / 647,852,169 拍，IPC 0.41186622005428525。
当前 RV64 为 700 MHz，Scored 为 71,090,721 条 / 494,678,053 拍。
指令数减少 61.945%，周期数减少 5.400%，因此 IPC 大幅下降而时间接近。

子项 fib：RV32 113,388,477 条 / 226,614,680 拍，RV64 7,704,261 条 / 96,821,238 拍。
它贡献两次 Scored 指令净减少量的 91.328%。其余子项并非全面提速，部分周期明显增加，
不能据总时间接近认定所有通路均正常。原始 manifest 尚未恢复，不宣称模型完全同条件。

代码证据：RV32 ARCH 使用 rv32i_zicsr_zifencei，编译器生成 __mulsi3、__divsi3 等软件
辅助调用；现有 RV32 镜像的 __mulsi3 是移位、条件加法及循环分支。RV64 当前 ARCH 使用
rv64im_zicsr_zifencei，归档 train 可见 mulw/divw/divu 等硬件指令。
fib 的 mult 内层包含矩阵元素乘法，M 扩展会改变实际退休指令数。
这个机制有源代码和反汇编证据，但没有旧 train 动态指令分类，不能把全部指令差额归给 M。

## 已复现的写模型问题

保持 ratio=7、8 个数据拍、相同数据、始终就绪的下游设备、末拍后 2 拍生成 B。
唯一变量是上游在相邻 W 之间增加 0 或 2 个 CPU 周期空档。

| 上游设置 | B 返回周期 | 相比连续发送增加 |
| --- | ---: | ---: |
| 连续发送 | 77 | 0 |
| 七个间隔各插入 2 CPU 拍 | 175 | 98 |

新增的是 14 个 CPU 周期，却按 7 倍增加到 98 拍。若设备服务行为不变、只计一次
上游 CPU 等待，应增加 14 拍；该隔离测试因此多算了 84 拍。
这里是 CPU 生产数据的空档，不是设备新增的服务周期。

根因在 axi4_delayer 的 write_device_time_increment：只在
write_data_ack_pending_q && !write_data_last_handshake_occurred_q 时暂停按比例累加。
没有 pending 确认而上游 WVALID=0 时仍累加 FREQUENCY_RATIO_SCALED，
将上游 CPU 空档当作设备时间。64→32 转换器的单项写数据缓冲清空后才能接收下一项，
也存在拍间空档；不能将这类 CPU/接口等待无条件放大。

复现源码与日志保存在 `result/verification/ipc-audit-20260927/`：
`axi4_write_gap_audit_tb.sv`、`write-gap-0.log`、`write-gap-2.log`、`write-gap-summary.json`。
相同二进制分别加 `+CPU_GAP=0`、`+CPU_GAP=2`。日志中的 PASS 仅指载荷、顺序与完成检查，
并非校准正确性通过。原连续 W 校准测试没有覆盖此情形。

这确认存在模型层面的放大，但不能用单次测试的 84 拍直接乘所有 train 缺失次数：
实际每笔事务的数据间隔、控制器状态和总线竞争不同。尚未测得该问题占 train 的百分比，
上述记录对应修复前模型；原始证据保持不变。随后已同步修复 RV64 与 RV32 的延迟器，
验证结果见下节。没有自动运行 train。


## 写通道修复及验证

两边 `ysyxSoC/perip/amba/axi4_delayer.v` 已同步修改：CPU 尚未提供写数据的空档
只按 CPU 周期累计；等待设备接受 AW/W、或接收地址及末拍后等待 B 的时间仍按
CPU/设备频率比累计。延迟器自身的 W 确认等待不重复累计，期间独立的 AW/B 工作仍计时。
CPU RTL、退休/周期统计口径、频率和缓存配置均未因此修改。

`test-soc-timing` 通过：原读写独立通道测试、64→32 位宽转换测试，以及 32 组写定时测试。
写定时矩阵覆盖频率比 1、2、2.5、7，初始与拍间 CPU 空档、设备 WREADY 反压、BREADY 反压。
七倍频率比、初始空档 1 拍时，连续写 BVALID 在第 71 拍，七个 2 拍空档使其变为第 85 拍；
只增加 14 拍。原模型对应第 77/175 拍，差异也包含初始 CPU 空档不再被乘七。
RV64 完整 SoC 的执行测试通过 DiffTest，包含 5421 个乘除法用例。

两边重新构建并运行完整 SoC MicroBench **test**，十项均通过，统计观察器开关一致性通过。
