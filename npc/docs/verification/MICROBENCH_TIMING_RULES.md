## 当前使用方式

默认性能入口为 `npc/scripts/run_microbench_perf.py`。它保留 MicroBench 原生定时器读取，
默认不编入额外 CSR 快照，在仿真端同步统计时间窗口内的周期与真实退休指令。

```sh
cd /home/yong/ysyx/ysyx-workbench-rv32-interview
python3 npc/scripts/run_microbench_perf.py --scale train --cpu-mhz 820
```

脚本先构建并归档，再启动仿真。`--prepare-only` 只准备文件；之后使用 `--resume 目录`
运行归档的模拟器和镜像，并核对哈希。默认采用 RV32 baseline、I-cache 256 B/1-way、
D-cache 256 B/2-way、BHT 16、BTB 16 项/2-way、RAS 4、SDRAM burst；CPU 820 MHz、
设备 100 MHz，CLINT 每 820 拍增加 1 微秒。输出目录不可覆盖，重测请创建新目录。

用户所说的“完成 train 的定时器时间”优先报告 **原生 Total time**，并同时给出该窗口
IPC；**Scored time** 与它的 IPC 单独列出，用于比较十个计分区间。JSON 中分别为
`total.timer_seconds` / `total.ipc` 与 `scored.timer_seconds` / `scored.ipc`。
`whole_program` 从复位释放到退出，`host_wall_seconds` 是宿主机运行模拟器所用时间。
这些数字不混用。

## 历史计时审计：本次发现

当前旧配置同时存在三个不同频率：CLINT 按 100 MHz CPU 换算微秒，AXI/APB
延迟模块按 `3037/1024` 倍拉长设备响应（对应 296.58203125 MHz CPU / 100 MHz
设备），本轮 STA 则检查 820 MHz。这不是一个已经校准到 820 MHz 的性能环境。

本轮保持相同镜像、SoC 和计时配置的优化前后周期数仍可比较；但这些周期数与
820 MHz 相乘或相除，不能直接形成符合课程访存条件的性能结论。旧记录保留，
不得将重新校准产生的周期变化记为硬件优化收益。

此前硬件优化和校准报告的数据来自带 CSR/定时器测量代码的 RISC-V 镜像。它们不是没有测量代码的
`run()` 净执行结果；CSR 的周期、指令快照也不是同一时刻原子采样。下面的同窗旁路
统计已经接入，短测结果见文末；新的 train 尚待手动运行，不能用新统计重新命名此前结果。

低侵入方案复审结论：保留基准原生定时器读取，去掉本项目额外加入的 PMU 快照和汇总，
以只读仿真观察统计周期与退休。基准计分窗口是主要性能口径；函数调用到返回的窗口
仅作独立诊断，不能替代原计分定义。下文末尾给出选择理由、采样约定和实施验收条件。

## 历史插桩版本：每个数字到底测什么

| 输出 | 计时范围与单位 | 用途 |
| --- | --- | --- |
| 宿主机 wall time | Linux 上等待模拟器运行的秒数，包含准备与校验 | 评估仿真效率 |
| PMU cycles / instructions / IPC | 十个 `run()` 外的成对 CSR 快照之间，IPC 为指令总数除以周期总数 | 比较 CPU 执行效率 |
| Scored time | 十个子项计分时间之和；不含 `prepare()`、`validate()`，含 PMU 读数及汇总开销 | 对应程序计分时间 |
| Total time | 主测试循环前后 uptime 之差，含准备、校验和循环内打印，不含此前启动阶段 | 对应更大的程序执行范围 |
| STA MHz | 综合网表在指定库、约束和分析条件下的时序结果 | 判定频率约束；不会自动配置模拟器 |

实现依据：`am-kernels/benchmarks/microbench/src/bench.c` 的 `run_once()`、
`bench_prepare()`、`bench_done()` 和 `main()`。本轮 `REPEAT=1`。
PMU 与 Scored time 的边界不同，因此二者不能要求逐周期完全相等。

`riscv32-ysyxsoc-sdram` 使用 `abstract-machine/am/src/riscv/ysyxsoc/timer.c`。
它读取本地 CLINT 的 0x02000048/4c，并把读数直接当作微秒。
`riscv32_npc_system` 默认传入 100,000,000 Hz 和 1,000,000 Hz，CLINT 每 100 拍
增加一次 mtime；软件没有读取 STA 报告，也没有自动除以 820 MHz。
本轮归档的 Verilator 生成代码也包含分频终值 99 和延迟比例 3037，确认这些默认值
进入了实际运行模型，而不只是未使用的源代码参数。

例如，基线 train 的 qsort 已完成窗口为 22,106,632 拍，打印 221.077 ms。
`22,106,632 / 100,000,000 = 0.22106632 s`，差额来自计时范围和微秒取整。
这与宿主机等待了多少分钟没有对应关系。

历史 `EXPERIMENT_LOG.md` 的 2026-08-26 完整 train 记录为 492,988,655 拍、
186,810,217 条指令、IPC 0.378934、Scored time 4929.979 ms；同样符合
100 MHz 打印口径。这是历史记录，不是本轮当前 RTL 重跑结果。

## 测量代码的开销与严格同窗统计

### 历史插桩镜像实际执行的内容

`read_pmu_snapshot()` 编译在 RISC-V workload 镜像内，由被测 CPU 执行，不是宿主机
通过 DPI 直接读取变量。已归档 train ELF 的该函数位于 0xa0001ca8；没有高位重试时，
函数体包含 6 条 CSR 读取、2 条条件分支、4 条 store 和 1 条 return，外部还有调用等
指令。十个子项各在开始和结束调用一次，共 20 次快照调用，不是每条 workload 指令
调用一次。读取 AM 定时器的 MMIO load 同样是真实执行的指令。

实际顺序是：prepare → 读取开始时间 → 开始 CSR 快照 → run → 结束 CSR 快照 →
汇总差值 → 读取结束时间 → validate。因此定时器、mcycle、minstret 各自取差值的
边界不完全相同，窗口内包含部分测量指令。

不能简单减掉一个固定的“读取开销”：CSR 在当前核上串行化，调用与存储会影响流水、
缓存和预测状态；插入代码也会改变代码布局。开销及扰动没有通过无插桩 A/B 定量分离，
不应宣称为零或给出未经测量的影响上界。现有固定镜像 A/B 仍是有效的插桩程序比较。

现有 `riscv32_sim_issue_window_monitor` 是旁路观察逻辑，不向 CPU 添加指令，但它用
已存在的 mcycle 读指令作为标记，仍观察带插桩程序；其 `issue` 类别统计发射事件，
不能普遍替代退休事件计数。现有宿主 `guest_inst_count` 按 commit valid 递增，也不能
无条件当作排除异常指令后的 minstret；严格退休事件应使用
`retired_instruction_occurred = commit_valid && !commit.trap_taken`。

### 函数区间的诊断约定（不作为默认计分边界）

程序镜像去掉本项目附加的 PMU 快照与汇总代码，保留并记录 benchmark 本身的程序内容。
只在仿真器或仿真专用模块中观察执行，不注入 CSR 指令、MMIO 标记或强制排空流水。
不能仅按 PC 是否位于函数地址范围计周期，那会漏掉等待、被调用函数和中断处理时间。

诊断指标对应十个 `run()` 的动态调用，定义为退休边界 ROI：

1. 从 ELF/反汇编识别调用点及返回位置；在外层 run 调用指令退休后打开窗口。
2. 从下一拍起，每个 CPU 周期均计入 C，包括没有退休指令的停顿周期。
3. 在同一窗口内，仅发生真实退休事件时增加 N。包含被调用函数、正常返回指令。
4. 外层 run 返回指令退休所在拍完成 C/N 累计后关闭窗口；不能把内部函数返回当成结束。
5. 总 IPC 为 `sum(N) / sum(C)`；固定频率下，窗口执行时间为 `sum(C) / f_cpu`。

这是明确的退休边界时间定义；调用退休前已经重叠发生的取指/执行工作不计入，不能把它
称为从冷启动执行孤立函数的全部延迟。窗口持续期间若发生中断，默认连同中断处理的
周期和退休指令一起计入；要排除干扰，应另设无中断实验条件，而不是静默扣掉周期。

辅助指标另设完整程序窗口：从系统复位释放后的首个完整工作周期，到正常退出标记
提交所在拍，包含启动、准备、run、校验及打印。退出异常标记的周期可以计入，但异常
指令不算退休。该窗口也不同于 benchmark 自带的 Total time，不混用名称。

两个指标的 C/N 都由同一时钟边沿、同一窗口使能累计，避免分别读 CSR 的边界偏移。
仿真器观察增加的是宿主运行开销，不增加被测 CPU 周期；时间仍需使用正确校准的模型。
定时器读数保留为软件可见时间的交叉检查；只有起止边界一致时才应要求与 C/f 对齐。

实施前需用有已知退休序列的短程序检查边界、无退休停顿、嵌套调用和异常事件，再重跑
无附加 PMU 插桩的完整 train。此前 0.171489 IPC、1.328498 s 计分时间保留为原镜像
结果，不自动作为该新协议的测量值。

## 低侵入测量方案复审

### 选择：保留基准定义，测量放到仿真侧

`am-kernels` 的 c4088239 版本原本就在 `run()` 前后调用 `uptime()`。所以不能把这部分
原生测时代码全部删除后，还声称测试的是相同的基准定义。当前工作树额外增加了
`read_pmu_snapshot` 和统计汇总代码，两者需要分开对待。

默认性能镜像应从固定基准版本构建，保留原生计时、准备、校验和打印；不添加 CSR
快照、自定义指令、MMIO marker、额外 fence，也不为方便观察而强制 noinline 或清缓存。
本项目的 PMU 插桩镜像继续保留为独立诊断/历史复现配置。恢复基准会改变二进制布局，
因此必须建立新基线；不能直接把新旧程序差异当作 CPU 硬件优化收益。

低侵入具体指对已固定程序镜像和 CPU 行为不再增加测量扰动，不代表原基准的计时指令
没有开销，也不代表仿真器统计没有宿主开销。

| 方案 | 对 CPU 执行的影响 | 本项目采用方式 |
| --- | --- | --- |
| 每个区间追加 CSR 快照 | 增加真实指令、串行化及存储，可能改变代码布局和缓存状态 | 保留作硬件计数器检查及历史复现，不作默认 |
| 自定义 marker、MMIO marker 或 ebreak 断点 | 增加指令/访存，可能强制停顿或改变异常状态 | 默认不采用；软件主动标记的特殊测试另行命名 |
| 给定开销常数或空函数结果后直接扣除 | 不能还原代码布局、流水、缓存与预测状态的扰动 | 不作为净性能依据 |
| 只读观察退休、时钟和原生定时器采样 | 不增加被测 CPU 指令，不向设计返回控制信号 | 默认方案 |
| 用函数入口/返回识别 ROI | 无额外指令，但需要处理内联、尾调用、嵌套和提前执行 | 可选诊断；不能冒充原生 Scored time |

### 输出必须带明确范围

1. **基准计分窗口**：用 MicroBench 原生起止定时器采样的同一对事件计算 C、N、T。
   十个子项各自统计，再汇总；输出 `score_cycles`、`score_retired`、`score_ipc`、
   `score_time_from_cycles` 和原生 `Scored time`。这是默认硬件性能比较的主要口径。
2. **完整程序窗口**：为避免外部复位与内部同步复位的歧义，明确从宿主撤销外部复位后
   的首个完整驱动周期开始，到正常退出提交所在拍完成计数。同步释放等待、启动、准备、
   校验和打印均计入；退出异常标记的周期计入，异常指令不算退休。它不等于原生 Total time。
3. **函数 ROI**：按上节单独命名；仅用于区分函数本体的瓶颈，不与以上时间直接混比。

同一窗口内，`IPC = N / C`，固定频率下 `T = C / f_cpu`；汇总采用 `sum(N)/sum(C)`，
不能平均各子项 IPC。C 包含窗口中所有时钟周期，不因 stall、cache miss、无退休或中断
而停止；N 只统计 `commit_valid && !commit.trap_taken`。中断处理在窗口内时默认一起计入，
另报中断次数；若需要无干扰实验，应记录其配置，而不是静默扣除时间。

### 原生计分时间怎样与 C/N 严格对齐

本项目 CLINT 在合法 32 位 mtime 低字读的 AR 握手时，把当时的 `mtime_q` 锁存成
整宽快照；随后的高字读使用同一快照。所以准确时间点是**低字读取被定时器采样的边沿**，
不是 UART 打印时刻，不是 R 通道消费时刻，也不是 load 最后退休时刻。后两者的延迟
可能变化，用它们代替会让统计边界与软件时间不一致。

仿真端持续维护总周期 C 和总退休数 N，每次发生上述采样事件，旁路保存 `(C,N,mtime)`。
全都按同一边沿的更新前状态快照，退休与周期随后正常更新。开始与结束快照作差，语义
统一为 `[开始边沿, 结束边沿)`：开始边沿的退休计入，结束边沿的退休不计入。若实现选择
其他边沿约定，必须同时修改所有计数和验证，不允许一项采样更新前、另一项采样更新后。

另用已固定 ELF 的反汇编和动态调用上下文，确认哪次定时器访问对应哪个子项的开始/结束。
初始化、main 总计时、子项计时和可能存在的其他读不能混为一对。计时读先产生总计数
快照，随后与最终成功退休的访存事件配对；异常或配对失败时不给出有效 score 结果。
不能只按“每两次 mtime 读”交替开关窗口，也不能把共同 timer 函数的一个 PC 当成唯一上下文。

实现分成通用只读事件采集与 MicroBench 专用事件配对，避免把基准名字/地址写进可综合
CPU。配对元数据必须绑定 ELF/bin 哈希，程序改变后重新生成并验证；无法确认内联/调用
关系或采样序列时明确报未支持，不能猜测窗口。默认仍能给出独立的完整程序统计。

如果 timer 每微秒加 1，单个窗口内 `Δmtime / 1 MHz` 与 C/f 的差应小于一个 timer tick
（同频率、相同采样边沿、无软件写 mtime 的前提下）。十项分别取差后累加，量化误差界
也应按窗口数量累计；不能因为打印时间与周期换算不逐位相等，就判断计数器有错。

### 实现约束与验收

复用现有仿真 wrapper 的 DPI/提交观察入口，在仿真边界补充真实退休标记和 timer 采样
事件。观察接口只读，不驱动 ready、valid、flush、cache 状态或中断；新增统计不进入
综合 filelist。不需要给 CPU 新增 PMU CSR 或基准专用端口，现有架构 PMU 仍然保留。
默认只累计总数和少量区间快照，结束时一次输出；完整逐指令 trace 只在诊断模式启用。

验收不是证明“工具运行成功”，而是检查以下具体问题：

- 已知短指令序列、连续 stall、同步异常、退出指令和同拍边界事件的 C/N 数量正确。
- 原生计时读的采样、响应、退休分属不同拍时，仍使用采样事件配对并满足 timer 量化界。
- main/初始化计时、十个子项及嵌套调用没有交叉配对；漏窗、重复窗、异常退出判为无效。
- 在**同一模拟器二进制、同一 workload 镜像**下开关 observer，架构/副作用事件摘要、
  输出、退出码和完成周期一致；observer 状态不得反馈进 CPU。对多个短程序及 MicroBench
  test 执行此检查，再对正式 train 的开关结果做验证，不能用两个不同镜像作无侵入证明。
- 检查综合输入/展开结果不包含新增观察状态；PPA 始终对应同一可综合核和缓存配置。
- 记录 RTL/SoC/ELF/bin/模拟器哈希、编译选项、输入、频率、访存延迟比例、复位/中断/
  cache 初始条件与统计边界；硬件 A/B 固定 workload 与环境，不混入计时配置变化。

零额外指令不等于访存模型一定准确。时钟频率与设备延迟校准仍单独验收；在旧比例下
得到 C 后，仅换一个 MHz 分母不构成新的真实性能测量。以下记录本次接入状态；历史
插桩成绩保留原有口径，新的低侵入 train 仍待手动运行。

参考：[官方 B4 的仿真环境 IPC 统计和访存校准要求](https://ysyx.oscc.cc/docs/2407/b/4.html)。
