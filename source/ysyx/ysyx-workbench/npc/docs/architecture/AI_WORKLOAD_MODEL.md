# AI 应用研究方向

状态：长期候选方向，具体需求尚未确定

最后更新：2026-09-05

## 1. 本文现在起什么作用

本文保存 CPU 完成后可以研究的 AI 应用问题。当前开发顺序仍是顺序核、单发射乱序核、
超标量乱序核，见 [架构与开发路线](ARCHITECTURE_PLAN.md)。

现在不要求选定模型、实现加速器或达到 AI 性能指标。普通程序、指令测试和针对依赖、分支、
访存的小程序，足以支持前几个阶段的设计验证。

过去讨论过本地多模态 AI Agent、AI PC、个人工作站和紧凑型推理节点，也提出过 3B～14B
参数的量化模型。这些保留为候选场景，不再作为首版 CPU 的固定产品要求。这里的 B 表示
十亿；模型参数数量只是资源预算的一项输入。

## 2. 到应用阶段再确定的内容

| 需要确定的事项 | 为什么需要它 |
| --- | --- |
| 一种主要设备和任务 | 明确使用环境、功耗约束和需要完成的工作 |
| 模型或算子、版本及输入规模 | 保证不同方案运行的是同一个任务 |
| 权重、激活、累加和 KV 数据的格式 | 明确存储量、算术精度和所需指令；量化权重不代表全部运算都是整数 |
| 运行库、编译器、ABI 和操作系统 | 确定需要实现的指令、特权级和软件接口 |
| 延迟、吞吐、质量和能耗指标 | 判断功能是否可用，以及优化是否有效 |
| 内存容量、有效带宽和共享方式 | 判断数据能否存下、能否及时送达计算单元 |
| CPU、向量单元和加速器分工 | 确定各部分需要完成的计算、搬运与同步 |

可以先选一个算子或缩小模型完成验证，再扩大输入。缩小规模的 RTL 测试只能证明对应
范围的功能和行为；完整模型的容量、吞吐和能效需要系统层面的验证。

## 3. 可选的负载

### 3.1 标量程序与运行时控制

- 分词（tokenizer）：把输入文本转换成模型使用的符号编号。
- 采样（sampling）：根据模型输出分数选择下一个输出符号。
- 内存分配、地址计算、数据布局转换和短循环。
- 加速器任务提交、完成通知、依赖管理及设备驱动。

这些程序可用于研究 CPU 的分支、缓存和标量执行能力。只有测量过它们占任务时间的比例，
才能判断改进 CPU 对整个任务有多大价值。CPU 等待加速器是可能的正常状态；目标是减少
任务延迟和能耗，不是让 CPU 始终忙碌。

### 3.2 数值计算与数据访问

- 矩阵乘法（GEMM）和矩阵向量乘法（GEMV）。
- 量化数据的解包、缩放与累加。
- attention 计算，以及复用历史键和值的 KV cache 访问。
- 图像、音频的前后处理。

需要用多个输入规模区分计算开销和访存开销。KV cache 是推理软件保存的数据，不是 CPU
的硬件缓存，不能与 I-cache、D-cache 的容量混用。

### 3.3 端到端生成任务

如果选择语言模型，再分别测量：

- 输入处理（prefill）：处理输入序列并建立生成所需状态。
- 逐步生成（decode）：使用已有状态继续生成输出。
- 初始化、模型加载和任务切换。

分别记录首个 token 的等待时间、后续生成速度、总任务时间、输出质量和能耗。不能只用
一个平均吞吐掩盖不同阶段的表现。[MLPerf Client](https://mlcommons.org/benchmarks/client/)
提供了本地生成式 AI 任务以及首 token 时间、生成速度等评价方式，可在选题时参考。

## 4. 可能的系统组织

一种候选方案是 CPU 运行控制软件和部分算子，向量或矩阵单元处理适合并行的计算，DMA
负责数据搬运。具体分工取决于运行库、算子规模和数据传输成本，不预先规定所有算子归属。

进入这类设计前，需要明确：

1. 命令如何提交，何时表示接收，何时表示执行完成。
2. CPU 和设备如何看到对方写入的数据，使用一致性硬件还是显式缓存维护。
3. 谁分配和释放缓冲区，任务取消及访问错误如何处理。
4. 标量执行、向量执行、DMA 和主存之间分别允许多少个未完成事务。

标准 RVV 可以作为向量指令接口的候选；矩阵接口和自定义指令待实际算子与软件方案确定后
评估。[Ara](https://github.com/pulp-platform/ara) 的 CVA6 与 RVV 协处理器组合可用于学习接口
和实现方式，但不构成本项目立即实现向量单元的要求。

## 5. 当前配置与未来系统的关系

当前 core 为 RV64，但物理地址宽度为 32 位，最多表达 4 GiB 物理地址空间；core AXI 数据
宽度为 64 位。它们是当前开发配置，不能据此声称已经能够运行大模型，也不妨碍先完成
顺序与乱序机制。

将来确定模型后，按权重、量化元数据、KV 数据、激活及运行时分别计算内存需求；按实际
数据路径、每次任务的传输量和实测有效带宽估算访问时间。若需求超出当前配置，再设计
更宽物理地址、不同内存接口或设备独立内存，并验证相应访问和错误处理。

## 6. 进入本方向时的第一项任务

选择一个可复现的程序，固定输入和软件版本，记录正确结果与时间组成。先回答“时间花在
哪里”，再安排 CPU、计算单元或内存系统的修改。M1～M3 不以完成这项任务为前提。
