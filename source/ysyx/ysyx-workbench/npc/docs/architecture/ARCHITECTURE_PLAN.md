# NPC RV64 CPU 架构与开发路线

状态：当前项目方向和阶段安排的依据

最后更新：2026-09-26

## 1. 我们要完成什么

本项目用于学习并独立实现 RV64 CPU。开发顺序是：**完成顺序核，再完成单发射乱序核，
随后扩展超标量执行。** 每个阶段都要得到能够运行程序、检查正确性并测量性能的实现。

边缘 AI 推理是长期应用方向。具体设备、模型规模、向量或矩阵单元、内存带宽和功耗目标，
留到应用研究阶段确定。它们不是当前顺序核和乱序核的开工或验收条件。

项目同时保留两类目标：

- **学习和实现目标**：掌握流水线、缓存、重命名、调度、顺序提交和错误恢复等机制。
  可以为完成这些目标引入结构，不必先证明某个 AI 程序需要它。
- **性能优化目标**：改善已选程序的执行时间、资源占用或能耗。声称某项修改带来收益时，
  必须给出相同测试条件下的测量结果。

“实现了乱序”与“乱序改善了目标应用”分别验收，不能相互替代。

## 2. 当前实现和限制

当前构建配置仍叫 `rv64-edge-ai`。这个名称用于选择现有构建配置，不表示已经支持 AI
推理或已经达到某项产品指标。设计目录为 `npc/vsrc/riscv`，模块和 package 使用 `riscv_`
前缀；整数架构由配置与 ISA 实现决定，当前为 RV64。原 `riscv32` 目录和模块前缀已统一迁移。
目录职责、全部模块和后续代码整理事项见 [设计模块总览](RTL_MODULE_MAP.md)。

下表对应 2026-09-26 的当前实现，包含已迁移的前端配置、乘除单元和 scoreboard。
本轮功能、周期、面积与时序证据见
[顺序发射与乱序完成验证](../verification/SCOREBOARD_INTEGRATION_2026-09-26.md)。

| 项目 | 当前情况 | 后续需要处理的内容 |
| --- | --- | --- |
| 指令集 | RV64IM、Zicsr 和 Zifencei 的实现，当前只取 32 位定长指令 | 按明确指令范围回归；A/C、浮点和向量扩展另立任务 |
| 流水线 | 单发射、顺序发射；Issue、ID/EX、独立 FU、scoreboard、顺序提交 | 完成相关、停顿、恢复和提交验证 |
| 异常和特权 | 机器态 CSR、同步异常和 `mret` 路径 | 已修正提交PC采样，当前35项ISA回归通过；机器态中断尚未接通，回归通过不等于全部特权行为已验证 |
| 数据与地址 | 整数和 core 访存数据为 64 位；物理地址为 32 位 | 当前物理地址空间上限为 4 GiB，其中还包含设备映射 |
| 缓存 | I-cache：1 KiB、4 路、32 B 行、分段访问 RRIP；D-cache：256 B、2 路、16 B 行；均为阻塞式 | 缓存容量采用 RV32 最终预设；[当前配置与验证](../verification/DCACHE_STYLE_SYNC_2026-09-25.md) |
| 分支预测 | BHT、BTB 和 RAS；默认分别为 16 项、16 项和 4 项 | 先验证预测、更新和恢复，再比较算法及容量 |
| 内存接口 | core 使用 64 位数据、32 位地址的 AXI4 接口 | 当前共享读通路最多一个未完成读事务；接口位宽不等于有效带宽 |
| 外部平台 | 通过宽度转换模块连接 32 位数据的 ysyxSoC 接口 | 保持平台转换与 core 内部设计分离 |
| 系统能力 | 尚无 S/U 特权级、MMU、完整操作系统运行环境或 AI 加速器 | 在相应阶段单独设计和验证 |

宽度配置见 [`riscv_config_pkg.sv`](../../vsrc/riscv/common/riscv_config_pkg.sv)，缓存和预测器
默认参数见 [`Makefile`](../../Makefile)。`XLEN`、物理地址宽度、指令宽度和总线宽度表达
不同含义，即使数值相同也不能合并。

此前用于物理寄存器、ROB 和访存队列的未使用容量常量及占位类型已在 RTL 清理中删除。
本轮已加入 8 项 scoreboard 承担在途结果管理和有序提交；物理寄存器堆、独立重命名表和 LSQ 仍未实现。

## 3. 开发阶段与完成条件

### M1：完成 RV64 顺序核

目标：得到正确、可回归、能够解释停顿原因的顺序流水线。

工作顺序：

1. 明确 RV64IM/Zicsr/Zifencei 的指令、CSR 和同步异常范围，检查不支持指令的处理。
2. 验证前递、写后读相关、load 等待、下游阻塞、分支错误恢复和顺序提交。
3. 验证 I-cache、D-cache、uncached 访问、AXI 反压和错误响应。
4. 接通机器态中断：中断源、待处理位、使能、接受时机、异常入口和返回须一起验证。
5. 回归 `fence.i` 清理失败时保持取指阻塞并重试的行为；平台重试上限和系统错误报告
   随平台需求完善，不能把自动重试写成完整系统容错。
6. 运行代表性程序，记录指令数、周期数、停顿事件，并建立综合面积与时序基线。

完成条件：

- 上述功能有对应的模块测试和整核回归，DiffTest 在声明的指令范围内通过。
- 没有已知的指令丢失、重复提交、错误路径写寄存器或写内存问题。
- 有可以重跑的软件与配置，以及对应的功能、周期、面积和时序记录。
- 未解决问题单独列出；若调整阶段范围，先更新本节，不能以“已完成”掩盖缺项。

不要求在 M1 运行 Linux 或 AI 模型，也不要求先加入 MMU、浮点、向量单元或非阻塞缓存。
形式验证可用于关键性质；单纯存在断言或形式验证源码不代表已完成证明。

#### 当前基线与下一步（2026-09-26）

当前为 RV64IM、Zicsr、Zifencei 单发射、顺序发射核，允许不同功能单元乱序完成。I-cache 为 1024 B / 4 路 / 32 B，
D-cache 为 256 B / 2 路 / 16 B；缓存配置、预测配置和基本旁路继承已经测量的 RV32 方案。
新增 ALU、分支、乘除单元与 RV64M 整核回归见
[执行单元验证](../verification/EXU_INTEGRATION_2026-09-26.md)，两核之间的实际差异见
[当前实现对照](RV64_RV32_CURRENT_COMPARISON.md)。历史 4 KiB D-cache 或加入 M 扩展前的
面积与时序不代表当前核。

**改造前、尚未加入 scoreboard 的 M 扩展基线**标准单元面积为 169,947.134 µm²。
其旧脚本曾返回 700 MHz 通过，但本轮发现该历史日志也有门控后寄存器缺少捕获时钟的诊断，
因此不能继续将该结果称为完整时序通过。历史面积仍可比较，旧频率结论须单独重验。
所有频率结果均须注明工艺角、时钟和输入输出约束；当前未做布局布线或多角签核。

当前采用 [CVA6 形式的 Issue 与 scoreboard](../microarchitecture/SCOREBOARD_DESIGN_RECORD.md)：
顺序发射、独立 FU 重叠、乱序完成、顺序提交。没有物理寄存器堆、独立重命名表或
绕过未发射指令的动态选择。同名写的多个结果保存在队列槽中，以最近写者标志决定前递。
LSU 可跨过已排除异常的较老纯运算，但访存之间仍逐条授权。

初版面积为 187,466.160 µm²，补齐时钟覆盖后通过 700 MHz 综合后完整验收。
其 WAW 和保守访存等待造成部分负载变慢；本轮优化及独立测量见
[第二轮验证](../verification/SCOREBOARD_WAITS_2026-09-26.md)。Issue 继续复用 ID/EX，
没有因为模块独立而增加流水级。本轮最终标准单元面积为 187,183.668 µm²，
在相同工艺角、理想时钟和输入输出约束下通过 700 MHz 综合后完整验收。两轮数据分别归档。

此后的工作包含：

1. **接通机器态定时器中断。** 当前 CLINT 只有只读计时值，mip 固定读零。补充比较寄存器、
   中断请求、CSR 使能、提交边界、mepc/mcause/mstatus 更新和 mret。覆盖屏蔽、重复响应、
   同步异常与分支恢复，明确已发出 store/MMIO 的完成与中断接受次序。
2. **扩充代表性软件测量。** 原有 35 个程序及新增 M 程序用于功能回归，不代表边缘 AI 吞吐。
   固定软件、输入、缓存、平台延迟与工具约束，分别测量相关等待、缓存缺失与分支恢复。
   原有 RV64I 软件保留相同二进制，新 M 程序使用 rv64im_zicsr_zifencei。
3. **按实际瓶颈选择执行单元实现。** 当前乘法器以并行部分积换取较少等待，MUL、DIV 与其他 FU 现可重叠，
   仍需结合数据依赖、队列容量和访存等待测量整体收益。后续可比较资源复用方案；同时报告周期、通过时序的频率和面积，不能仅凭
   源码变短、寄存器减少或单个专项变快判断优劣。
4. **达到 M1 完成条件后进入 M2。** 先明确重命名、ROB、结果返回和恢复规则，第一版保持
   单发射与保守访存顺序。验收年轻就绪指令能跳过尚未发射、等待操作数的老指令，仍按序提交。
   超标量与 AI 专用执行单元继续按后续阶段推进，不要求现在定案。

中断语义参考 [RISC-V 机器态规范](https://docs.riscv.org/reference/isa/priv/machine.html)，
乘法与除法范围参考 [M/Zmmul 规范](https://docs.riscv.org/reference/isa/v20240411/unpriv/m-st-ext.html)。

### M2：完成单发射乱序核

目标：允许较年轻且操作数已准备好的指令先执行，同时按程序顺序提交。
第一版取指、译码、重命名、发射和提交宽度均保持为 1，以控制首次实现的复杂度。

分步实现：

1. **重命名**：物理寄存器、架构寄存器到物理寄存器的映射表、空闲寄存器表及回收规则。
2. **顺序提交**：重排序缓冲区（ROB）保存指令先后顺序、完成状态和异常，只有队首能够提交。
3. **乱序调度**：发射队列记录依赖；结果返回后唤醒等待指令，并选择就绪指令执行。
4. **访存管理**：load/store 队列保存地址、数据、年龄和完成状态。第一版允许保守地保持
   访存顺序；等待 load 时，应能够让无依赖的标量指令继续执行。
5. **错误恢复**：恢复寄存器映射、空闲表和各队列，丢弃错误路径结果。进入实现前选定
   恢复方式；可以先采用逐项回退，再评估快照恢复，不强制第一版实现单周期恢复。

执行结果可以在提交前写入物理寄存器，但不能提前改变已提交的寄存器映射和异常状态。
store 和有副作用的 MMIO 访问必须在确认不会被撤销后才对外发出。第一版可在 ROB 队首
授权 store、等待访问结果后退休；若以后改为退休后排空写缓冲，须另行定义写错误的处理。

完成条件：

- 保留 M1 的指令语义和回归，增加重命名、队列满空、资源回收、异常及分支恢复测试。
- 用定向程序和执行事件证明：年轻的独立指令确实能越过等待中的老指令执行。
- 能证明错误路径结果和 store 不会造成不可撤销的副作用。
- 比较 M1 与 M2 的周期、面积和时序，说明收益与代价；不要求每个程序都加速。

ROB、LSQ 的容量以及预测器大小在进入相应模块设计时确定。多 MSHR、推测访存、复杂预测器
和 Linux 都不是第一版乱序执行的必要条件。

### M3：扩展超标量乱序核

目标：在 M2 稳定后，让处理器能够每周期发射多条指令，并处理新增的端口冲突和同周期依赖。

先选择小宽度的明确配置，再逐步扩展取指、译码、重命名、发射和提交。各处宽度分别定义，
不要求同时扩宽，也不要求数值始终相同。

必须验证同周期寄存器依赖、资源分配、多结果返回、部分提交、异常优先级和恢复。
寄存器堆多端口或分 bank、多 MSHR、写缓冲和更强预测器是候选实现，按瓶颈和时序选择，
不作为必须一次加入的功能清单。

完成条件：多发射行为有实际事件记录和定向测试；完整回归通过；与 M2 在可比条件下记录
执行时间、面积和时序差异。不能只用发射宽度或峰值 IPC 说明性能。

### M4：研究系统软件与 AI 应用扩展

M1～M3 完成后，再围绕具体应用确定系统要求，详见 [AI 应用研究方向](AI_WORKLOAD_MODEL.md)。
Linux 所需的特权级、地址转换、原子操作及启动环境，可以根据软件学习任务另行安排，
不必与某一次流水线改造同时完成。

进入 AI 研究时，先选择设备、模型或算子、运行库、数值格式和评价指标，再决定向量单元、
矩阵单元、DMA 与内存共享方式。3B～14B 模型仅保留为过去讨论过的候选范围。

## 4. 模块职责

| 部分 | 主要职责 | 设计记录 |
| --- | --- | --- |
| 预测器、IFU、取指缓冲 | 预测下一取指地址，跟踪请求，丢弃旧取指路径的响应 | [分支预测](../microarchitecture/BRANCH_PREDICTION_DESIGN_RECORD.md) |
| I-cache | 指令缓存查找、缺失回填和失效处理 | [I-cache](../microarchitecture/ICACHE_DESIGN_RECORD.md) |
| 译码、寄存器读取、执行与提交 | 生成操作、选择操作数、执行指令，按程序顺序确认结果 | [流水线](../microarchitecture/PIPELINE_DESIGN_RECORD.md) |
| LSU 与数据存储子系统 | load/store 格式处理，按地址属性选择 D-cache 或 uncached 路径 | [D-cache](../microarchitecture/DCACHE_DESIGN_RECORD.md) |
| AXI 适配、仲裁与地址路由 | 转换事务、共享下游端口、选择目标并返回错误 | [AXI4 互连](../interconnect/AXI4_ARCHITECTURE.md) |

每组状态由明确模块负责更新。内部请求/响应结构表达取指或访存含义，AXI 通道仅由相应
适配及互连模块处理。后续模块是否能直接复用，需结合新增并发、恢复和时序要求重新检查。

当前 Issue 与 scoreboard 管理顺序发射和在途结果，旧集中式 hazard controller 不再位于活动后端。
进入 M2 后，再引入重命名、动态选择和更复杂的恢复，不能把本轮的乱序完成写成已经实现乱序发射。

## 5. 保留的验证与性能工具

- DiffTest：与参考模型比较指令执行后的架构状态。
- RTL 定向测试和随机反压：检查局部行为与接口协议。
- 断言和形式验证：检查关键性质；记录实际运行范围和未证明项。
- `cachesim`、`branchsim`：利用访问或控制流记录筛选缓存和预测器方案。
- AXI/APB 延迟模型：模拟等待与反压，检查接口稳定性和延迟敏感度。
- 综合和静态时序分析：检查存储实现、面积和关键路径。

仿真统计模块不进入综合 core。软件可见的架构计数器属于硬件功能，与仿真监视器分开。
模型的命中率、预测准确率或估算周期不能直接当成 RTL 性能结论。

## 6. 后续工作的判断规则

1. 先说明任务属于功能实现、学习实验、错误修复还是性能优化，再制定对应的验证要求。
2. 当前阶段只固定实际需要的接口和配置，不为尚未设计的加速器增加空端口或大批占位状态。
3. 修改接口时，同步更新受影响的父模块、断言、测试和文档。
4. 比较两个版本时控制软件、输入、平台延迟和工具约束；每个版本的周期、面积和时序
   必须对应各自的 RTL。实验变量要明确记录，不能混用不同版本的结果。
5. 性能计数在事件发生的模块中定义。退休指令数在提交边界计数，缓存缺失和 AXI 握手
   各按自身事件计数，不能统称为“都在提交时统计”。
6. 当前规范与历史记录分开。旧计划标明已被替代，历史实验保留日期、配置和结果。

具体实施方法见 [开发流程](../development/DEVELOPMENT_PROCESS.md)。
