# 程序仿真与性能测试

更新：2026-09-27。当前主工程只有一套程序仿真环境：完整 ysyxSoC。

## 固定的性能比较规则

正式负载统一为 MicroBench **train**。`test` 仅用于短回归和快速定位，不用它预测 train
的收益。二者是同一程序的不同输入规模，会改变循环次数、数据量和缓存行为。

正式 A/B 的主指标是 **Scored 窗口的执行时间与周期数**；同时列出同窗退休数、IPC、
各子项和原生 Total 时间。整程序计数包含启动，只用于诊断。IPC 不是单独的验收目标：
ISA 或编译器减少了指令数时，IPC 可能下降而执行时间缩短。

每轮比较遵循以下规则：

1. 使用相同 Flash 镜像（bin、ELF 的 SHA256 一致）、相同 train 输入、相同启动布局。
2. 固定完整 SoC、设备及颗粒模型、AXI/APB 校准实现、统计代码、CPU 700 MHz / 设备
   100 MHz / 定时器 1 MHz，以及 SDRAM burst 模式。700 MHz 是控制变量，不是新的 STA 结论。
3. 每次只修改一个待验证的 CPU 设计因素。缓存/预测器参数可以是该因素，必须在比较中列明；
   未研究的参数保持相同。保留修改前后的归档，禁止覆盖旧数据。
4. 正确性先通过，再看同频 train 的周期/时间变化。正式物理收益还要比较相应版本的面积、
   完整 STA 和 `周期数 / 通过时序的频率`；改变 CPU 频率时须重新仿真校准后的 SoC，
   不能把原来周期数直接除以新频率。
5. 改动设备模型或测量方法属于**测试环境修正**，须给修改前后两个 CPU 版本都重新测量，
   不能把模型变化算作 CPU 优化。RV32I 与 RV64IM 镜像不同，属于跨 ISA 系统比较，
   以相同算法/输入下的执行时间为主，不称为同镜像硬件 A/B。

`result/performance/soc-20260927T043307177887Z/`。

## 校准的含义与验证边界

设备参考频率为 100 MHz，CPU 评估频率为 700 MHz，二者周期长度不同。
设备处理访问用了 k 个设备周期，对应时间为 `k / 100 MHz`，CPU 经过 `7k` 个周期。
仿真设备与 CPU 原本随同一个时钟推进，因此延迟器补足等待；不是每次 miss 固定增加 7 拍，
也不是把 CPU 内部的命中、流水线等待全部乘 7。

课程要求读事务从 VALID 开始计时，逐个读 beat 按频率比校准，读写独立计时，写数据也须校准。
当前协议测试验证了受测条件下的行为。**计时器/周期一致仅证明测量换算正确，不能证明所有
设备等待都建模正确。** 修改校准器之前，应区分 CPU 产生数据的间隔、互连等待、设备服务
时间和延迟器自身插入的等待，检查是否重复放大。

2026-09-27 定向审计在修复前模型中复现校准问题：8 拍写事务中仅在相邻 W 之间各加入 2 个
CPU 周期的上游空档，共 14 拍，B 返回时间却从第 77 拍增加到第 175 拍，多了 98 拍。
校准器把这类上游空档也乘了 7。旧模型只排除了自身插入的等待，没有区分上游暂时不提供数据
的 CPU 时间。原连续 W 测试未覆盖这个条件，不能据其通过认定模型完全正确。
该行为可能影响含数据拍间隔的写回；真实 train 中的具体贡献尚未量化。
当前 train 结果保留为旧模型诊断证据，暂不作为经过物理模型审计的最终性能结论。
计数复核与复现见 [IPC 与校准审计](IPC_AUDIT_2026-09-27.md)。

## 运行入口

在 `ysyx-workbench/npc` 中执行：

```bash
make perf
```

默认运行 MicroBench train。开发阶段的短测试使用 `make perf PERF_SCALE=test`。
本次维护只运行短测试，train 由用户启动。测试输出和源文件快照自动保存在
`result/performance/soc-时间戳/`，最终结果是该目录的 `report.json`。
归档用于复现，不是另一套配置或另一条性能测试路径。

软件统一使用 `ARCH=riscv64-npc`，默认编译 RV64IM 程序并在 ysyxSoC 上运行：
Flash 从 `0x30000000` 启动，启动代码将运行镜像复制到 `0xa0000000` 的 SDRAM，
清零 BSS 并执行 FENCE.I；栈位于 8 KiB SRAM。其他程序可在 AM 目录执行
`make ARCH=riscv64-npc run`，或把构建好的 Flash 镜像交给 `make sim FLASH_IMG=...`。
旧 `sim-npc`、`sim-am`、`build-npc` 只是同一 SoC 入口的兼容名称。
调试、波形、ISA DiffTest 和乘除法集成程序也使用完整 SoC。

standalone 源码及旧结果保留用于追溯，已撤下常规程序构建/运行入口。
协议、模块、异常注入的定向 testbench 是定位问题的单元验证，不作为程序性能成绩。

## 存储路径与官方要求

官方依据：[B4 性能优化和简易缓存](https://ysyx.oscc.cc/docs/2407/b/4.html)。
按 CPU 与 100 MHz 设备的频率比校准设备访问，正式性能测试使用校准后的 SoC train。

```text
IFU → I-cache ─────────────────────────────┐
LSU → D-cache / uncached ─────────────────┤
                                         ↓
                               I/D AXI 仲裁与本地 CLINT 路由
                                         ↓
                                  AXI64 → AXI32
                                         ↓
                                   ysyxSoC 互连
                    ┌────────────────────┴────────────────────┐
            AXI 延迟器 → SDRAM 控制器 → SDRAM       AXI/APB → APB 延迟器 → 外设
```

Cache 命中的内部时序不乘设备频率比。Miss 的真实开销由仲裁、设备访问、回填和反压共同产生。
AXI 读从 VALID 首次出现计时，对各个响应拍分别校准；读写控制独立。
写通道将下游已接收的 W 延迟确认给上游，并阻止重复转发，从而限制后续写拍；
计算后续拍和 B 的目标时间时排除本延迟器已插入的非末拍等待，避免重复放大。
B 不得在上游末个 W 完成前返回。整数与小数比例均有定向检查。

RV32 工作区现已同步 W/B 校准，两个工作区使用同一份 AXI 延迟实现。
历史结果必须按具体记录区分，不能把所有 0.35、0.41 IPC 都归为 test：
用户提供且历史会话再次确认的 2026-09-22 train 为 Total IPC 0.411866220 / 0.899794 s，
Scored IPC 0.357247174 / 0.726274 s，原目录为
`passive-train-20260922T071755Z`。原目录不在当前工作区；现已从历史工具输出恢复 report，确认 CPU 720 MHz、
Scored 186,810,327 条 / 522,916,178 拍。manifest 与镜像指纹仍待恢复，不能套用 8 月配置。
这次 train 早于最终冻结提交 fbe7824，不能代表冻结后源码重测成绩。

## 时间、周期和指令的统计

基准程序保留原生 AM_TIMER_UPTIME 计时，默认不插入额外 CSR 采样指令。
只读观察器在 CLINT 接受 mtime 低字读取的边沿保存 timer、cycle 与已退休指令数，
待相应 load 成功提交后确认样本。脚本绑定 ELF 的原生调用位置，拒绝不认识的编译布局。

每个测量区间计算 `IPC = Δinstret / Δcycle`，并要求
`abs(Δtick / 1 MHz - Δcycle / CPU频率) < 1 μs`。
Scored 是十个执行窗口的周期与指令分别求和再相除；Total 与整程序窗口另列，不能混用。
脚本核对十项都通过、GOOD TRAP、23 个 timer 样本、原生打印时间、频率与镜像哈希。
短测试可用 `python3 scripts/run_microbench_perf.py --scale test --verify-observer`
比较观察器开关前后的输出及架构摘要，不改变程序指令。

## 比较两次归档

日常运行仍只有 `make perf`；以下命令只读取结果，不创建另一种仿真环境：

```bash
make perf-compare BASELINE=result/performance/旧结果目录 CANDIDATE=result/performance/新结果目录
```

比较脚本核对规模、ISA、软件镜像、频率、设备模型和测量源码指纹，检查成功状态与计数一致性。
不满足同条件比较时直接拒绝输出提升百分比；满足时输出 Scored/Total 周期变化、时间和 IPC，
并列出硬件配置变化。Total 含计时结果打印，退休数可能稍变；Scored 退休数变化则拒绝比较，
先调查程序、输入或行为是否改变。该检查不代替 DiffTest，也不证明模型已覆盖所有边界情况。

## 写通道时间归属修复（2026-09-27）

写事务计时区分三个来源：AW/W 已提供而等待设备，或 AW 与末 W 都接收后等待 B，
按设备频率比累加；没有上述设备工作、且上游没有提供地址/数据时，按一个 CPU 周期累加；

现有事务状态足以判断，不增加流水级或改动 CPU。每笔事务完成及复位按原规则清状态。

## 同一 RV64 核的软件乘除法对照

`make perf PERF_ISA=rv64i` 将应用、AM 和 klib 全部重新编译为
`rv64i_zicsr_zifencei`，ABI 仍是 LP64；默认 `PERF_ISA=rv64im` 使用
`rv64im_zicsr_zifencei`。保留 CSR 与 FENCE.I 是启动和运行环境的需要。
硬件乘除法器、scoreboard、缓存、700 MHz 评估点、延迟器和存储位置不随此选项改变。
RV64I 软件运行时通过软件例程完成乘除法；不是改成 RV32，也不是移除硬件模块。

在 npc 目录顺序执行（train 由用户运行）：

```bash
make perf PERF_SCALE=train PERF_ISA=rv64i
make perf PERF_SCALE=train PERF_ISA=rv64im
```

每次自动新建时间戳归档，避免覆盖结果。不要同时运行两条构建命令，因为应用和库共用构建目录。
镜像强制完整重编，manifest 记录实际软件 ISA、完整构建命令和静态 M 指令数；RV64I 镜像
如果仍含 M 指令，脚本在仿真前报错。恢复旧归档时仍使用归档镜像，不能通过传入新 ISA 切换它。

比较相同 Scored 窗口的周期和时间；软件乘除法会改变退休指令数，不能用 IPC 高低判断加速。
同频加速比为 RV64I 周期数 / RV64IM 周期数。这个对照包含乘法与除法的软件替换，
也包含代码布局、分支和缓存行为变化，不能单独测得乘法器延迟或 scoreboard 的净收益。
旧延迟模型的 train 不作为本次对照；两组均应在当前模型重新测量。
通用 `perf-compare` 要求相同 ISA/镜像，因此会拒绝这组有意改变软件 ISA 的实验，不应绕过其检查。
